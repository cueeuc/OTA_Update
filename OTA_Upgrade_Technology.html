Chapter 01

基础认知：OTA 到底是什么

这一章只建立概念，不涉及任何代码或芯片型号。读完后你应该能用自己的话解释"OTA"这个词，并知道它在整个设备生命周期中扮演什么角色。

1.1 OTA 是什么

OTA（Over-The-Air，空中下载技术）

严格定义是：设备通过无线链路远程接收并安装新固件。但在工程口语里，"OTA"已经泛化为"不用把设备拆回来、不用专用烧录器，就能把新固件装进设备"的一整套机制——所以它既包括 Wi-Fi / BLE / 4G 这类真正的"空中"，也包括"上位机通过串口给设备升级"这种行业习惯叫法。

换个角度说，OTA 交付的不是"一个文件"，而是一种能力：产品卖出之后，厂商仍然能修改设备里的软件。这个能力一旦缺失，设备的软件状态就被冻结在出厂那一刻，此后发现的每一个 Bug、每一个安全漏洞都只能靠召回解决。

几个容易混淆的词

固件升级是统称（把新程序写进设备就算升级）；FOTA（Firmware Over-The-Air）特指"固件本身的空中升级"，车规领域常用；SOTA（Software Over-The-Air）多指"应用层/配置层更新"，常见于车机与智能座舱；DFU（Device Firmware Update）是 Nordic 等厂商对"设备固件升级"的称呼；ISP（In-System Programming，在系统编程）指用烧录器或调试口直接写芯片，属于本地操作，不算 OTA。

一个必须说清楚的术语边界：严格意义上，"串口 OTA"并不是"空中"升级——它靠一根物理线缆。业内这么叫，是因为它复用了 OTA 的全部软件机制（Bootloader 接收、校验、写 Flash、置标志、重启切换），只是把"下载链路"从无线换成了串口。本书沿用这个习惯叫法，但你要知道它在物理层属于 ISP / 本地升级，不享受"远程"带来的规模收益。
是什么OTA 是一套"设备 + 网络 + 固件管理"协同工作的机制，让已经离开生产线的设备依然可以被改写软件。
为什么设备出厂之后，软件问题（Bug、功能缺失、安全漏洞）依然会暴露，而把它们收回来重新刷机在经济上和物流上都不成立。
怎么工作设备主动或被动地把"当前版本号"告诉服务器，服务器比对后下发新固件包，设备下载、校验、写入 Flash，然后重启进入新版本。

一次 OTA 升级必须凑齐的三样东西

ELEMENT 01

固件包（Firmware Package）

升级的"货物"。不只是一个 bin 文件，还包含版本号、目标型号、长度、校验值与签名等元信息，让设备能判断"这包是不是给我的、对不对"。

ELEMENT 02

传输通道

运货的车。本手册分两类：串口（UART）——一根线直连，适合产线与实验室；无线——Wi-Fi / BLE / 4G，适合大规模在网设备。

ELEMENT 03

升级入口（Bootloader / IAP）

收货并安装的人。设备里的 Bootloader 负责擦除 Flash、接收数据、校验固件、更新启动标志，最后把控制权交给新程序。

1.2 OTA 技术是如何出现的

OTA 不是凭空发明出来的，它是"设备数量爆炸"和"网络能力普及"这两件事共同逼出来的产物。下面这条时间线解释了今天的设备为什么几乎都带 OTA。

  • 1990s – 2000s

    PC / 手机时代：人工刷机是常态

    固件升级靠串口线或数据线，由厂商工程师完成。设备量少、人力成本还能承受，所以没有人觉得"远程升级"有必要。

  • 2000s 后期

    设备批量出货，人工刷机不可持续

    MCU 成本下降，智能家居、传感器、工业网关开始一次出货几千台。为了修一个小 Bug 召回上万台设备在经济上直接不成立，"远程改软件"成了刚需。

  • 2010s

    Wi-Fi 模组便宜 + 物联网云平台成熟

    联网成本降到几块钱，云端能管理百万级设备，于是形成"设备—云—固件仓库"的闭环。OTA 从"某个品牌的私有方案"变成"行业标准能力"。

  • 2014 / 2016

    SoC 把 Wi-Fi 与 OTA 集成进芯片

    2014 年的 ESP8266 与 2016 年的 ESP32 这类芯片出厂即自带 OTA API 与分区表机制，开发者调几个函数就能升级，OTA 从"系统工程"降级为"一行配置"。

  • 2016 至今

    方案标准化：BLE DFU、模组 AT 指令、安全启动

    Nordic 的 DFU 方案、4G Cat.1 模组的 AT 指令升级、芯片级安全启动（Secure Boot）陆续成熟，OTA 同时要满足"能升级"和"只允许升级可信固件"。

  • 2020s

    从"能升级"到"可治理"

    Matter、MCUboot、Mender/RAUC、OTA 云平台把灰度发布、A/B 回滚、版本矩阵、审计日志做成标准能力。法规也开始介入（欧盟 CRA、车载 UN R156），OTA 从开发者的便利工具变成产品合规义务。

1.3 OTA 主要解决什么问题

① 修 Bug 与补功能

现场设备被发现有缺陷时，第一反应不再是"拆下来重刷"，而是推一个 OTA 包过去，把维护周期从"周"压缩到"分钟"。

② 降低维护成本

一台设备装在井盖、路灯杆或客户家里，现场施工一次的成本可能是软件修复成本的几十倍。OTA 把"现场作业"变成"发个包"。

③ 统一版本管理

服务器能统计每台设备的当前版本，判断还有多少设备停留在有漏洞的旧版本上，为安全响应提供依据。

④ 差异化配置与后续扩展

产品出厂后还能调整参数、启用新功能或切换区域策略，不必为每个小差异单独生产一批硬件。

1.4 为什么嵌入式设备特别需要 OTA

PC 的 OTA 失败了大不了重装系统，嵌入式设备升级失败往往意味着设备变砖——设备彻底无法使用，除非有人把它拆下来用编程器重刷。所以嵌入式 OTA 不只是"能不能升"，更重要的是"失败了怎么办"。

部署环境恶劣

设备可能在户外、高温、粉尘、弱电网环境。升级必须容忍断网、断电、传输中断，并在设备重启后能自我恢复。

资源极度受限

Flash 可能只有几百 KB，RAM 可能只有几十 KB，固件包必须"塞得下"，甚至需要差分升级来压缩体积。

生命周期极长

工业设备在役十来年，这期间芯片厂、模组厂、云平台都可能停止服务。OTA 是把"维护能力"留在自己手里的唯一手段。

1.5 OTA 的基本工作流程

不管底下是串口还是 Wi-Fi，一次完整升级都可以拆成四个阶段。理解这张闭环图，后面的所有细节都只是它的展开。

PHASE 1

版本协商

设备上报自身版本与型号，服务器决定"要不要升、升到哪一版"。

PHASE 2

固件传输

把固件包通过串口或无线链路搬到设备本地缓存区，支持分块与断点续传。

PHASE 3

落盘与校验

校验完整性、验签，通过后写入目标分区并设置升级标志。

PHASE 4

切换与确认

重启后由 Bootloader 选择新固件启动，新固件自检成功才算升级完成。

初学者最容易混淆的一点：下载成功 ≠ 升级成功。只有到第 ⑧ 步"新固件自检通过并被标记为有效"，服务器上这台设备的状态才真正变成"已升级"。中间任何一步失败，设备都必须能安全地回到旧版本继续工作。

本章小结

  • OTA 的核心价值是远程与规模化，而不是"能升级"本身。
  • 严格来说串口 OTA 属于本地 ISP，但它复用了 OTA 的全部软件机制，是理解原理的最佳入口。
  • 一次升级必须凑齐三样：固件包、传输通道、升级入口（Bootloader）。
  • 完整闭环是 8 步，其中"自检并标记有效"才是真正的完成点。
  • 嵌入式场景的特殊性在于：失败必须可恢复，这决定了后面所有设计。

Chapter 02

OTA 核心基础：Bootloader、Flash 与固件

OTA 的所有动作，最终都归结为三件事：往 Flash 里写数据、判断数据对不对、决定启动哪一段代码。本章把这三件事背后的角色和结构讲清楚，并给出可以照着抄的跳转代码、链接脚本和分区表。

2.1 Bootloader 的作用

Bootloader（引导加载程序）是设备上一段出厂时烧好、日常运行中不会被擦除的小程序。它永远比 APP 先运行，并且拥有整个 Flash 的读写权限。所有"升级请求"最终都要由它来执行。

是什么一段独立于业务 APP 的引导代码，通常几 KB 到几十 KB，放在 Flash 的最前面，出厂固化后不再改动。
为什么APP 是可以被随意覆盖甚至写坏的，没有一个"永远可信"的程序把关，设备就可能再也起不来。
怎么工作上电后先跑 Bootloader，它读升级标志、校验待升级固件、决定跳转到哪一段 APP，出问题还能负责恢复。

① 上电自检与准备

检查 Flash、RAM、电源状态是否正常，初始化最基本的时钟与串口，为可能的升级做准备。

② 判断是否要升级

读取参数区里的"升级标志"与启动次数。有标志才进入升级或试运行流程，没有就直接跳转 APP，几乎不占用开机时间。

③ 擦除、写入与搬运

擦除目标分区，把缓存区的新固件搬运到 APP 区，或直接边收边写。这是 Bootloader 掌握 Flash 写权限的原因。

④ 校验与启动选择

对固件做完整性校验，确认可用才跳转；校验不过就尝试备用分区或进入恢复模式。

⑤ 设置启动标志

标记"下次启动要走新固件"。这一位标志是升级流程中最后写的，写它的瞬间就是升级的提交点。

⑥ 异常恢复

升级中断、固件启动失败时提供恢复通道（串口恢复、按键进入下载模式、回到旧分区），避免设备变砖。

2.2 APP 程序与 Bootloader 的关系：跳转与向量表

可以把嵌入式设备想象成一家门店：Bootloader 是永远在岗的门卫与店长，负责开门、验货、决定今天开哪个门；APP 是店里的业务，随时可以被替换，但开门权在店长手里。

对比项Bootloader（引导程序）APP（应用程序）
位置Flash 起始区，固定不变Flash 中部的 APP 分区
谁写入出厂烧录，日常不擦除（仅专用升级流程会动它）出厂烧录，之后可被 OTA 覆盖
运行时机每次上电时最先运行，之后退出被 Bootloader 跳转后一直运行
主要职责启动判断、固件校验、擦写 Flash、异常恢复业务功能、通信、云端交互
资源占用极小（通常 < 32KB），必须极度精简可用资源多，受限于 Flash 与 RAM 总量
出错后果写坏则设备无法启动，只能拆机重刷写坏可由 Bootloader 重新刷入
中断向量表位于 Flash 起始，由它自己使用位于 APP 分区起始，需 SCB->VTOR 重定位

跳转是怎么完成的（Cortex-M 示例）

很多人第一次写 Bootloader 会卡在"跳过去就 HardFault"。原因几乎总是同一个：只改了 PC，没有改栈顶，也没有重定位向量表。Cortex-M 的启动过程约定死了两件事：

  • 复位后，CPU 从向量表第 0 项读初始栈顶（MSP），从第 1 项读复位向量（即 Reset_Handler 地址）。
  • 向量表的地址由 SCB->VTOR 决定，复位默认是 0x00000000（通常映射到 Flash 起始）。跳到 APP 前必须把它改成 APP 分区的起始地址，否则 APP 里第一个中断会跳回 Bootloader 的向量表，直接跑飞。
/* bootloader/jump.c —— 跳转到 APP 的最小可靠实现 */
typedef void (*app_entry_t)(void);

int jump_to_app(uint32_t app_base)
{
    uint32_t sp = *(volatile uint32_t *)(app_base);        /* 向量表[0]：初始 MSP */
    uint32_t pc = *(volatile uint32_t *)(app_base + 4);    /* 向量表[1]：Reset_Handler */

    /* 1) 合法性检查：栈顶要落在 RAM 内，复位向量要带 Thumb 位 */
    if (sp < RAM_BASE || sp > (RAM_BASE + RAM_SIZE)) return -1;
    if ((pc & 0x1u) == 0) return -1;                        /* Cortex-M 只跑 Thumb */
    if (pc < app_base || pc >= app_base + APP_MAX_SIZE) return -1;

    /* 2) 关中断、停 SysTick，避免跳转瞬间被中断打断 */
    __disable_irq();
    SysTick->CTRL = 0; SysTick->LOAD = 0; SysTick->VAL = 0;
    for (int i = 0; i < 8; i++) { NVIC->ICER[i] = 0xFFFFFFFFu; NVIC->ICPR[i] = 0xFFFFFFFFu; }

    /* 3) 把 Bootloader 用过的外设恢复默认，否则 APP 里初始化可能失败
          （典型症状：APP 里串口收不到数据、SPI 不工作） */
    HAL_DeInit();          /* 或逐个 RCC 复位、关闭已开时钟、关闭 DMA */

    /* 4) 向量表重定位 —— 漏了这一步，APP 里第一个中断就跳飞 */
    SCB->VTOR = app_base;
    __DSB(); __ISB();

    /* 5) 设栈顶，跳到复位向量 */
    __set_MSP(sp);
    ((app_entry_t)pc)();

    return 0;              /* 正常情况下不会返回 */
}
三个高频坑：① 忘了 SCB->VTOR，APP 能跑但一进中断就死；② 忘了关外设/关中断，APP 里外设初始化返回 HAL_BUSY 或第一次串口收发丢字节；③ APP 的链接脚本仍然从 0x08000000 开始，烧进去后与 Bootloader 重叠，表现为"跳过去跑的是 Bootloader 自己"。第 ②、③ 点分别在 2.6 展开。

2.3 Flash 存储器与程序存储布局

Flash 是一种非易失性存储器（断电不丢数据），可反复擦写。嵌入式设备的程序、配置、固件包通常都存在 Flash 里。

擦除与写入的单位不同

Flash 通常按扇区擦除（片内常见 1KB / 2KB / 4KB / 128KB，外部 SPI NOR 常见 4KB / 64KB），但按字节、半字或页写入。写入前必须先擦除（擦除把整片置为 0xFF，写入只能把 1 变 0）；擦除本身没有前置条件，但擦掉的整段内容会一起丢失。

有寿命上限

每个扇区的可擦写次数有限：片内 MCU Flash 常见 1 万次量级，外部 SPI NOR 常见 10 万次量级。频繁写日志、频繁升级同一分区会消耗寿命，所以参数区应做磨损均衡（见 2.7）。

擦写会短暂阻塞

擦除一个扇区可能需要几十到几百毫秒，其间 CPU 无法从该 Flash 读代码（read-while-write 限制），这限制了 Bootloader 升级代码不能太大，也决定了擦写期间必须继续喂狗。

典型的 Flash 存储布局（自上而下）

分区内容升级时是否变化
Bootloader 区引导程序、升级协议实现不变化（除非做 Bootloader 自身升级，见 2.8）
参数区设备参数、当前版本号、升级标志、回滚计数变化：升级前后更新标志与版本号
APP 区（Slot A）业务固件变化：被新固件覆盖
下载区（Slot B / Cache）接收中的固件包变化：每次升级写入，升级后清理
文件系统区用户数据、配置、离线缓存、日志一般不参与升级，需单独保护
密钥 / 只读区公钥、设备证书、序列号、加密密钥永不变化（写保护 / OTP）
参数区为什么单独存在？因为它是 Bootloader 和 APP 之间的"约定纸条"。升级标志、目标版本号、失败重试次数都必须放在 APP 之外，否则升级还没开始 APP 就已经被覆盖了，无处可查。

2.4 固件（Firmware）与固件包结构

固件是固化在设备存储器里的软件及配套资源的统称：一段可执行程序，加上它需要的字库、图片、参数模板、协议栈配置等。多数 MCU 的 Flash 里，固件 = 程序代码段 + 启动代码 + 数据段。

用于 OTA 的固件包通常不是裸的 bin 文件，而是一个带"信封"的包。这个信封让设备可以在写入之前就做出判断。

一个可以直接抄的头部定义

/* 固件包头部：固定 64 字节，便于按扇区对齐存放 */
#define FW_MAGIC        0x57465531u    /* "FWU1" */
#define FW_HDR_SIZE     64u

typedef struct {
    uint32_t magic;         /* 魔数，快速判断这是不是一个固件包 */
    uint16_t hdr_size;      /* 头部长度，便于将来扩展字段 */
    uint16_t hdr_version;   /* 头部格式版本，不是固件版本 */
    uint32_t fw_version;    /* 固件版本号，建议用 主.次.补丁 打包进 32 位 */
    uint32_t hw_id;         /* 目标硬件型号/硬件版本，防止刷错板子 */
    uint32_t payload_size;  /* 固件本体长度（不含头部与签名） */
    uint32_t payload_crc32; /* 本体的 CRC32，用于落盘后完整性校验 */
    uint32_t build_time;    /* 构建时间戳（UTC），便于追溯 */
    uint32_t flags;         /* bit0: 已加密  bit1: 差分包  bit2: 需强制升级 */
    uint8_t  payload_hash[32]; /* 本体的 SHA-256，验签的输入 */
    uint8_t  reserved[4];
} fw_header_t;              /* 4+2+2+4+4+4+4+4+4+32+4 = 68 → 按 64 对齐取舍 */
头部里最容易被漏掉的两个字段：hw_id 与 hdr_version。hw_id 防止"把 4G 版固件刷进 Wi-Fi 版"这种量产事故；hdr_version 让你在三年后扩展头部字段时，旧设备还能读懂新包的公共部分，而不至于直接拒绝。

2.5 固件下载、写入、校验与启动的基本过程

把上面几块拼起来，一次升级在设备内部实际发生的是这么一件事：

  1. 下载：先把固件完整搬到本地

    固件包经串口或无线链路分块传到设备，暂存在下载区或 RAM 缓冲。此时 Flash 里的 APP 还没被动过，设备仍可正常运行旧版本。

  2. 校验：确认搬来的东西没坏、没被篡改

    分块传输时逐块校验（防传输错误），落盘后整包校验（防存储错误），再验证数字签名（防人为篡改）。任何一层不过关就丢弃固件包，保留旧版本。

  3. 写入：把固件落到它该待的分区

    擦除目标分区后写入。写入顺序至关重要：先写固件数据，最后写升级标志。这样任何时刻断电，重启后 Bootloader 都只会运行那个经过完整校验的旧固件。

  4. 启动：重启并交棒给新固件

    置位升级标志后复位，Bootloader 读取标志、校验新分区，通过则跳转；新 APP 启动后做一次自检并把该版本标记为"有效"，升级才算真正完成。

记住这条主线：下载 → 校验 → 写入 → 启动。任何一种 OTA 方案，区别都只在"下载用什么链路""校验做到什么强度""写到哪里"，主线流程本身是通用的。

2.6 链接脚本与内存布局

这是初学者最容易跳过、又必然踩坑的一节。Bootloader 和 APP 是两次独立编译，它们各自有一份链接脚本。如果 APP 的链接脚本仍然从 Flash 起始地址开始，那么 OTA 写进去的固件就会和 Bootloader 重叠——表现为"升级后设备变砖"或"跳转后跑的还是 Bootloader"。

规则只有一条：APP 的 ORIGIN 必须精确等于它所在分区的起始地址，且向量表必须放在分区最前面。

/* app.ld —— APP 的链接脚本（GCC / GNU ld 节选）
   假设：片内 Flash 256KB @0x08000000，Bootloader 占前 64KB，
        参数区占 8KB，APP 从 0x08012000 开始。 */
MEMORY
{
  FLASH (rx)  : ORIGIN = 0x08012000, LENGTH = 184K
  RAM   (rwx) : ORIGIN = 0x20000000, LENGTH = 128K
}
ENTRY(Reset_Handler)

SECTIONS
{
  /* 向量表必须是分区里的第一段内容，否则 VTOR 指向它也没用 */
  .isr_vector : { KEEP(*(.isr_vector)) } > FLASH

  .text : {
    *(.text*) *(.rodata*) *(.glue_7) *(.glue_7t)
    . = ALIGN(4);
    _etext = .;
  } > FLASH

  .ARM.exidx : { *(.ARM.exidx*) } > FLASH

  _sidata = LOADADDR(.data);
  .data : { _sdata = .; *(.data*) . = ALIGN(4); _edata = .; } > RAM AT > FLASH
  .bss  : { _sbss = .; *(.bss*) *(COMMON) . = ALIGN(4); _ebss = .; } > RAM
}

光改链接脚本还不够，启动文件里也要告诉系统向量表的偏移。以 STM32 HAL 工程为例，在 system_stm32xxxx.c 里：

/* 偏移量 = APP 分区起始地址 - Flash 起始地址 */
#define VECT_TAB_OFFSET   0x00012000U
/* SystemInit() 里会执行： SCB->VTOR = FLASH_BASE | VECT_TAB_OFFSET; */
顺手要做的三件小事：① 在 APP 里放一个常量记录自身版本号与构建时间，OTA 上报版本时直接读它，避免"代码里写死的版本号和实际固件对不上"；② 让链接器生成 .map 文件并归档，出问题时要靠它定位是哪个段越界；③ 用 arm-none-eabi-size 检查固件大小，并在 CI 里设置"超过分区 90% 就报警"的阈值。
部分芯片对分区头部还有硬性要求：ESP32 要求镜像开头有 image header（魔数 0xE9 + 段数 + 校验和），并在末尾附加 SHA-256；i.MX RT 要求 IVT + Boot Data；部分 MCU 要求向量表附近放一个校验字。做这些平台时，不要手写头部，用官方工具（esptool、elftosb、MCUboot 的 imgtool）生成。

2.7 分区表与升级元数据设计

前面反复说"把标志写进参数区"，但参数区到底长什么样？这一节给出一份可以直接用的设计。元数据是 OTA 的"账本"，它记错一次，设备就可能反复重启或误判升级成功。

第一步：定义分区表

分区名起始地址大小说明
boot0x0800000064 KBBootloader，含串口/无线升级协议
otadata0x080100008 KB元数据双副本（各 4KB，交替写）
app0（Slot A）0x0801200088 KB应用固件 A
app1（Slot B）0x0802800088 KB应用固件 B
nvs0x0803E0008 KB业务参数、日志、离线缓存

注意 app0 与 app1 必须等大且按扇区对齐。A/B 大小不一致会导致"回滚目标装不下"，是双分区方案最常见的翻车点。

第二步：定义元数据结构

/* otadata —— 放在 0x08010000，双副本各占一个 4KB 扇区 */
#define OTA_MAGIC        0x4F544131u    /* "OTA1" */

typedef enum {
    SLOT_EMPTY   = 0,   /* 空白或已擦除 */
    SLOT_PENDING = 1,   /* 已写满并通过校验，等待首次启动验证 */
    SLOT_TRIAL   = 2,   /* 正在试运行：本次启动尚未被 APP 确认 */
    SLOT_VALID   = 3,   /* APP 自检通过并确认，永久有效 */
    SLOT_BAD     = 4    /* 校验失败或试运行失败，禁止再启动 */
} slot_state_t;

typedef struct {
    uint32_t magic;          /* OTA_MAGIC */
    uint16_t meta_ver;       /* 元数据结构版本，便于升级格式 */
    uint8_t  active_slot;    /* 0=A  1=B：本次应该启动哪个 */
    uint8_t  reserved0;
    uint32_t seq;            /* 单调递增：两个副本谁更新，看它 */
    uint32_t boot_attempts;  /* 当前 SLOT_TRIAL 已尝试的启动次数 */
    uint32_t rollback_cnt;   /* 历史回滚次数，用于告警与统计 */
    struct {
        uint32_t version;    /* 该分区固件版本 */
        uint32_t size;       /* 固件长度 */
        uint32_t crc32;      /* 固件 CRC32 */
        uint8_t  state;      /* slot_state_t */
        uint8_t  reserved[3];
    } slot[2];
    uint32_t crc;            /* 本结构的 CRC32，覆盖上面所有字段 */
} ota_meta_t;

第三步：写入策略（磨损均衡 + 原子性）

  1. 双副本交替写

    两个 4KB 扇区轮流使用。每次更新时写"当前 seq 较小的那份"（即旧的那份），写完回读校验，成功后才作废另一份。这样任何时刻至少有一份完整可读。

  2. 用 seq 判断新旧

    不要用"哪个 CRC 对就用哪个"来判断——两份都可能 CRC 正确。必须靠单调递增的 seq，取 seq 更大且 CRC 正确的那份。

  3. 整体 CRC 放在结构末尾

    写入顺序是"先写前面所有字段，最后写 crc"。这样如果写到一半断电，crc 仍是 0xFFFFFFFF，读出时判为无效，自动回退到另一份副本。

  4. 磨损估算

    一次升级写 1 次元数据，即使每天升级一次，两个 4KB 扇区各承受约 180 次/年擦写，对 1 万次寿命的片内 Flash 完全无压力。真正需要磨损均衡的是高频写的业务参数，不是 OTA 元数据。

为什么 boot_attempts 必须存在元数据里而不是 RAM？因为"新固件启动失败"的典型表现是复位——RAM 内容会被清掉或不可信。只有落在 Flash 里的计数器，才能在连续第 3 次启动失败时告诉 Bootloader："这个版本试过三次了，放弃它，回滚。"

2.8 Bootloader 自身如何升级

前面所有方案都有一个隐含前提：Bootloader 是好的。可 Bootloader 也有 Bug、也需要支持新 flash 型号、也要修安全漏洞。而它一旦升级失败，设备就永久变砖——这是整个 OTA 体系里风险最高的操作，必须单独设计。

方案一：两级 Bootloader（推荐）

ROM 里固化的 BL0（或芯片自带的 ROM Boot）永远不动，只负责"校验并跳转到 BL1"；可升级的是 BL1。BL1 坏了，BL0 还能通过串口/USB 重新灌入 BL1。这是唯一能做到"BL 升级失败仍可救回"的结构。

方案二：BL 分区双备份

把 BL 分成 bl_a / bl_b 两份，元数据里记录哪份有效。升级时写另一份，校验通过后切标志。代价是浪费一份 BL 的空间（通常几十 KB），对 Flash 紧张的设备要权衡。

方案三：ROM 下载模式兜底

很多芯片出厂就带不可擦除的 ROM Bootloader（ESP32 的 download mode、STM32 的 system memory、Nordic 的 ROM DFU）。只要保留 BOOT 引脚或特定串口命令能进这个模式，BL 就永远可救。代价是需要现场接触设备。

单 BL 设备怎么做自升级

如果硬件只有一份 BL、也没有 ROM 兜底，升级流程必须极其小心，核心矛盾是：不能擦除自己正在执行的扇区。可行做法是"RAM 中转"：

  1. APP 或串口先把新 BL 写进一个暂存分区

    暂存区可以是 Slot B，也可以是专门划的 bl_staging。此时旧 BL 完全没被动过。

  2. 校验新 BL 的完整性与签名

    BL 是信任链的根，验签标准必须比 APP 更严。校验失败就到此为止，一切照旧。

  3. 置 bl_update 标志，复位

    标志写完后才允许进入下一步。此时断电，设备仍启动旧 BL，只是会再次尝试升级。

  4. 旧 BL 把"搬运程序"拷进 RAM 并跳过去执行

    搬运程序运行在 RAM 中，因此可以安全地擦除 BL 所在扇区，把暂存区的新 BL 逐块写入。

  5. 写完后回读校验，再清 bl_update 标志

    校验不通过就保持 bl_update 标志并尝试重写；连续失败则放弃，设备退回旧 BL（旧 BL 内容此时可能已被破坏，所以这一步必须配合方案一/二/三中的至少一种）。

结论：除非芯片自带 ROM 下载模式，不要做"单 BL 原地自升级"。量产产品的最优解是"ROM 兜底 + 两级 BL"：ROM 负责把设备救活，BL0 负责验证 BL1，BL1 负责 OTA。三层里任何一层损坏，都还有下一层可以覆盖它。

本章小结

  • Bootloader 是设备上唯一"永远可信"的代码，也是所有升级动作的执行者。
  • 跳转的三件套：合法性检查 → 关中断关外设 → SCB->VTOR 重定位 + 设 MSP，缺一个就 HardFault。
  • APP 的链接脚本起点必须等于分区起点，向量表必须在分区最前面。
  • 元数据是 OTA 的账本：双副本 + seq 单调递增 + 整体 CRC 放最后，三者缺一不可。
  • Bootloader 自升级是最高风险操作，量产方案应该是"ROM 兜底 + 两级 BL"。

自测

  1. 跳到 APP 后能跑，但一进中断就死，最可能是什么原因？
    2. 查看答案

    没有设置 SCB->VTOR。中断发生后 CPU 仍去 Bootloader 的向量表取入口地址，跳到了错误的位置。

  1. 元数据为什么要存两份，且用 seq 判断新旧？
    2. 查看答案

    一份可能在写入途中被断电损坏；用 CRC 只能判断"是否完整"，不能判断"哪份更新"，所以必须靠单调递增的 seq。

  1. 单 Bootloader 设备为什么不能"原地自升级"？
    2. 查看答案

    擦除 BL 所在扇区时，正在执行的代码就在这个扇区里，CPU 无法继续取指，程序立即崩溃。必须把搬运程序放到 RAM 执行，或者留一份备份 BL。

Chapter 03

串口 OTA 升级（UART OTA）

串口 OTA 是最"古老"也最可靠的一种升级方式：一台电脑、一根线、一套握手协议，就把新固件送进设备。它是理解 OTA 原理的最佳起点，也是所有设备最后的救命通道。

3.1 串口 OTA 的基本概念

串口 OTA，指 PC 端的上位机工具通过 UART（通用异步收发传输器） 与设备内部的 Bootloader 直接对话，把固件包一块块传过去，由 Bootloader 负责写入 Flash。它不需要网络、不需要服务器，也不需要任何中间件。

是什么PC 升级工具 + 设备 Bootloader 通过串口点对点完成的一次固件更新，中间没有网络环节。
为什么很多设备出厂时并没有联网能力，或者现场根本不具备网络条件，但固件仍需可被更新——串口是最低成本、最容易调试的通道。
怎么工作工具发握手请求，设备进入下载模式，双方约定协议与参数，然后逐块传送并逐块校验，最后设备写入 Flash 并重启。
产线批量烧录 实验室调试 无网设备 现场应急救援 Bootloader 自举（见 2.8）

3.2 UART 在 OTA 中的作用

UART 是一种最简单也最常见的点对点串行通信方式，只需要两根信号线（发送 TX、接收 RX）加一根公共地线（GND），没有时钟线，双方靠约定好的波特率来同步每一位数据。

波特率
每秒传输的符号数，常见 115200 / 460800 / 921600 / 2000000。收发双方必须一致，否则收到的是乱码。
数据格式
常见 8N1：8 个数据位、N 表示无校验（None）、1 个停止位；每字节前面还有 1 个起始位，因此每字节实际占 10 bit。
校验方式
若需要奇偶校验则写成 8E1（偶校验）或 8O1（奇校验），此时每字节占 11 bit，吞吐要相应打折扣。
流控
RTS/CTS 硬件流控，或用 XON/XOFF 软件流控；简单方案常直接用 ACK/NAK 应答代替。
双工能力
UART 是全双工的，同一根线上既能发也能收，但升级过程中通常采用"一问一答"的方式避免冲突。

波特率直接决定升级速度

因为每个字节要占 10 bit，理论最高速率 = 波特率 ÷ 10。实际传输中还要算上协议头、应答与等待，通常只能达到理论值的 70%~85%。

≈11.5 KB/s
460800 8N1
≈46 KB/s

为什么更高波特率不是越大越好？波特率越高，信号边沿越密，对线缆质量、接地和时钟精度要求越高。线长、干扰大时会出现随机乱码或丢字节——表现为"偶尔升级失败"，极难排查。实验室短距离可用 921600，现场长线建议保守选择 115200。

3.3 硬件连接与握手协议

PC 早已不再自带串口，所以需要一块 USB 转串口芯片（CH340、CP2102、FT232 等）来完成 USB 与 UART 的电平转换。

常见的两类握手方式

① 通用文件传输协议

直接使用 Xmodem / Ymodem 这类现成协议：上位机发文件，接收方逐块回 ACK（好）或 NAK（重发），传输完再回一次结束符。优点是工具现成、协议成熟；缺点是不方便做签名验证与断点续传，也没有"型号/版本"这类业务字段。

② 自定义帧协议

厂家自己定义帧头、命令字、序号、长度、CRC 等字段。优点可以携带型号、版本、签名等完整信息，便于做安全和断点续传；缺点需要自己写上位机工具。

Xmodem 与 Ymodem 的帧长什么样

这两种协议之所以能活到今天，是因为实现极简、容错够用。理解它们的帧结构，你自己写的私有协议基本就是它的变体。

协议帧结构单帧数据特点
Xmodem SOH | seq | ~seq | 128B data | CRC16 128 字节 最经典。序号取反（~seq）用于快速判错；Xmodem-1K 把数据段扩到 1024 字节，吞吐提升明显
Ymodem 先发一个含文件名与大小的 block 0，之后按 Xmodem-1K 传数据 1024 字节 能带文件名与长度，适合一次传多个文件；文件名段可被"借用"来传版本号等业务信息
自定义 0xAA55 | cmd | seq | len | payload | CRC16 任意 可控性最强：可加签名、可断点续传、可双向心跳。代价是要自己写两端

Xmodem 的关键控制字符：ACK=0x06、NAK=0x15、CAN=0x18（连发两个表示取消）、EOT=0x04（结束）。接收方主动发起——设备先发 'C'（0x43）表示"我准备好了，请用 CRC 校验发"，上位机才发第一帧。

3.5 Bootloader 如何接收并写入新固件

Bootloader 内部通常是一个明确的状态机，每个状态只做一件事，收到超时或错误就回到空闲状态等待下一条指令：

STATE

IDLE 空闲

等待上位机的握手或升级请求，带超时判断，避免设备被"卡"在升级界面。

STATE

ERASE 擦除

擦除目标分区。擦除耗时较长，因此应先擦再收，别让上位机白等。

STATE

RECEIVE 接收

逐块收、逐块校验，出错就请求重传，累计写入偏移量。

STATE

VERIFY 校验

对已收到的完整固件做整包 CRC 校验，必要时验签。

STATE

WRITE 写入

把缓存区的固件搬运到 APP 区，或在接收时直接写入目标分区。

STATE

DONE / ERROR

成功则置升级标志并复位；失败则记录错误码、保留旧固件、回到 IDLE。

两种写入策略的取舍

策略做法优点风险
直接写 APP 区 边收边写，目标就是正在运行的分区 不需要额外的下载区，省 Flash，代码简单 传输中断 = APP 区半新半旧，设备直接变砖
先写下载区再搬运 先完整收进空闲分区并校验，通过后再擦除并搬运 传输中断不伤旧固件，可靠性高，可天然支持回滚 需要约一份固件大小的额外 Flash 空间

Bootloader 侧伪代码

注意三个细节：等待升级请求只在"该等"的时候等（否则每次开机都白等 3 秒）；重传必须有次数上限；验签在写标志之前完成，且标志永远是最后一个字节。

/* Bootloader 侧的接收与写入逻辑（示意） */
#define MAX_RETRY   5

static int ota_receive_all(void)
{
    int retry = 0;
    uint32_t offset = 0;

    flash_erase(SLOT_B_ADDR, SLOT_B_SIZE);          /* 先擦，避免边收边等 */
    ota_send_ready();                               /* 告诉上位机：可以发了 */

    while (ota_recv_block(&blk) == OTA_OK) {
        if (crc16(blk.buf, blk.len) != blk.crc) {
            if (++retry > MAX_RETRY) return OTA_ERR_TOO_MANY_RETRY;
            ota_send_nak();                         /* 本块损坏，要求重发 */
            continue;
        }
        retry = 0;                                  /* 收到好块就清零 */
        if (flash_write(SLOT_B_ADDR + offset, blk.buf, blk.len) != 0)
            return OTA_ERR_FLASH_WRITE;
        offset += blk.len;
        ota_send_ack();
    }

    /* 整包校验：先确认没坏，再确认可信 —— 顺序不能反 */
    if (crc32(SLOT_B_ADDR, offset) != pkg.crc32)
        return OTA_ERR_CRC;
    if (!signature_verify(SLOT_B_ADDR, offset, pkg.signature))
        return OTA_ERR_SIGN;

    return OTA_OK;
}

int main(void)
{
    /* 关键：只有在"升级标志置位"或"按键进入下载模式"时才等待上位机，
       否则直接跳 APP —— 否则每次开机都会慢 3 秒。 */
    if (boot_flag_set() || download_pin_pressed()) {
        if (ota_receive_all() == OTA_OK) {
            meta_set_slot(SLOT_B, SLOT_PENDING);    /* 提交点：标志最后写 */
            meta_commit();
        } else {
            ota_report_error();                     /* 保留旧固件，不写标志 */
        }
    }
    system_reset();
}
一个容易被忽略的工程细节：正在擦写的 Flash 扇区，其内容在擦除期间无法被读取执行。因此 Bootloader 的升级代码要么运行在 RAM 中，要么必须放在不会被擦除的另一个扇区里。这也是 Bootloader 代码量要严格控制的原因之一。

3.6 上位机工具怎么实现

设备端写完了，PC 端还得有个工具。这一步常被教材跳过，但实际项目里"协议两端都自己写"才是常态。一个够用的上位机只有四件事：串口收发、帧封解包、超时重传、进度与日志。

用现成工具（最快跑通）

SecureCRT / Tera Term / Xshell 都内置 Xmodem、Ymodem 传输。设备端实现好接收逻辑后，菜单里选"发送文件 → Ymodem"即可。适合验证阶段，无法定制业务字段。

用 Python 自己写（推荐）

pyserial 十几行就能跑通自定义协议；打包成 exe（PyInstaller）后交给产线或售后使用。开发快、易改、易加日志，是中小团队的最优解。

# host_tool.py —— 自定义帧协议的最小上位机（Python 3 + pyserial）
import serial, struct, time, zlib

FRAME_HEAD = b'\xAA\x55'

def build(cmd, seq, payload=b''):
    body = struct.pack('<BBI', cmd, seq, len(payload)) + payload
    return FRAME_HEAD + body + struct.pack('<H', zlib.crc32(body) & 0xFFFF)

def wait_ack(ser, seq, timeout=1.0):
    """等待设备回 ACK(seq) ；超时或收到 NAK 返回 False，由上层决定重传"""
    deadline = time.time() + timeout
    while time.time() < deadline:
        hdr = ser.read(2)
        if hdr != FRAME_HEAD:
            continue
        cmd, rseq, ln = struct.unpack('<BBI', ser.read(6))
        data = ser.read(ln + 2)
        if rseq != seq:
            continue
        return cmd == 0x06                       # 0x06 = ACK, 0x15 = NAK
    return False

def upgrade(port, fw_path, chunk=1024, max_retry=5):
    ser = serial.Serial(port, 115200, timeout=0.1)
    ser.write(build(0x01, 0, b'HELLO'))          # 握手
    if not wait_ack(ser, 0):
        raise SystemExit('设备无响应：检查是否进入下载模式')

    with open(fw_path, 'rb') as f:
        data = f.read()
    total, seq = len(data), 0
    for off in range(0, total, chunk):
        seq = (seq + 1) & 0xFFFFFFFF
        blk = data[off:off + chunk]
        for attempt in range(max_retry):
            ser.write(build(0x02, seq, blk))
            if wait_ack(ser, seq):
                break
            print(f'\r重传 seq={seq} ({attempt + 1}/{max_retry})', end='')
        else:
            raise SystemExit(f'块 {seq} 重传 {max_retry} 次仍失败')
        print(f'\r{min(off + chunk, total) * 100 // total:3d}%  {off + chunk}/{total}', end='')

    ser.write(build(0x03, seq + 1, struct.pack('<I', total)))   # 结束命令
    print('\n传输完成，等待设备校验并重启')
上位机必须做的三件事：① 超时重传（串口丢字节是常态，不重传就会卡死）；② 日志落盘（现场升级失败时，唯一的证据就是这份日志）；③ 进度显示（升级耗时可能几十秒，没有进度用户会以为卡死而拔线，这本身就是一次人为故障）。

3.7 串口 OTA 的优缺点与适用场景

优点

  • 不需要网络，产线、实验室、野外都能用
  • 带宽稳定，速率可预期，排障时能实时看到每一帧
  • 实现简单、工具成熟，学习成本最低
  • 现场设备失联时，是最后的"救命通道"

缺点

  • 必须物理接触设备，无法远程批量升级
  • 人工与工时成本随设备数量线性增长
  • USB 转串口驱动、端口占用、波特率匹配等环境问题多
  • 串口速率远低于无线，大固件耗时长

典型适用场景

产线烧录

批量生产时把固件一次性写入每台设备。

研发调试

固件迭代频繁，串口能连着看日志、能反复重刷。

无网设备

不联网的采集器、网关、控制器，升级靠现场工程师。

应急恢复

无线升级失败后，用串口把设备救回来。

本章小结

  • 串口 OTA = 上位机 + Bootloader 点对点，是理解所有 OTA 机制的最小可用原型。
  • 8N1 每字节占 10 bit，理论吞吐 = 波特率 ÷ 10，实际约 70%~85%。
  • Xmodem/Ymodem 够用且现成；要带版本、签名、断点续传就得自定义帧协议。
  • Bootloader 只在"该等"的时候等，重传必须设上限，标志永远最后写。
  • 上位机三件套：超时重传、日志落盘、进度显示。

自测

    2. 查看答案

    115200 ÷ 10 ≈ 11.5 KB/s，500KB ÷ 11.5 ≈ 43 秒。算上应答与擦除开销，实际约 50~60 秒。

  1. 为什么 Bootloader 不能每次上电都等上位机 3 秒？
    2. 查看答案

    这会让每台设备每次开机都慢 3 秒，用户体验极差，也不符合"升级是低频事件"的事实。应该只在升级标志置位或进入下载模式时才等待。

  1. 上位机不做超时重传会发生什么？

    串口丢一个字节，设备就一直等这个块，上位机一直等 ACK，双方互锁。表现为"进度条卡住"，且必须人工介入。

Chapter 04

无线 OTA 升级（Wireless OTA）

无线 OTA 是"规模化物联网"真正的玩法：设备自己上网取包，人不用靠近设备。它与串口 OTA 的差别，在流程图上看只是第 ③ 步的画法变了。

4.1 无线 OTA 的基本概念

无线 OTA，指设备通过 Wi-Fi、蓝牙（BLE）、蜂窝网络（4G/5G）等无线链路，从服务器下载并安装新固件。设备与服务器之间通常还存在一个OTA 云平台，负责版本管理、固件分发与设备状态统计。

是什么设备自主联网、远程升级固件的机制，规模化运维的核心手段。
为什么成千上万台设备分布在城市各处，人工上门一次的成本，往往比重新生产设备还高。
怎么工作设备查询版本 → 服务器下发固件地址与签名 → 设备下载到缓存 → 校验验签 → 写入 Flash → 重启切换。

4.2 Wi-Fi、BLE 与蜂窝网络在 OTA 中的应用

三种主流无线通道的差别，本质上是速率、功耗、连接成本、覆盖范围四者之间的取舍。

Wi-Fi OTA

设备连上路由器后，通过 HTTP/HTTPS 或 MQTT 从服务器下载固件。速率最高，适合有稳定网络、固件较大的设备。

典型速率 数十 ~ 数百 KB/s
代价 依赖路由器，功耗较高

BLE OTA

通过低功耗蓝牙传输固件，常见于 Nordic DFU 与 SMP/MCUmgr 方案。低功耗是核心优势，适合电池供电的穿戴与传感器。

典型速率 2 ~ 90 KB/s（随 MTU 变化）
代价 受 MTU 限制，常需手机 App 参与

蜂窝（4G/5G）OTA

通过 4G Cat.1 / NB-IoT 模组，用 AT 指令触发模组下载并写入外部 Flash，再由 MCU 复位加载。覆盖最广，不依赖 Wi-Fi。

4.4 无线 OTA 的完整升级流程

4.5 固件下载、缓存、校验、写入与重启

无线升级最关键的技术点是缓存——固件必须先落到某个可靠的地方，写入目标分区前不能直接覆盖运行中的程序。

缓存位置做法适用情况
外部 Flash 空闲区用独立 Flash 存整包固件，写完再搬运最常用，支持大固件，可实现 A/B 双分区
内部 Flash 空闲分区片内 Flash 划出一段空间专门存下载包没有外部 Flash 时使用，但占用宝贵的片内空间
RAM 缓冲先在 RAM 里攒齐，攒不满就升级不了仅适合很小的固件或增量补丁

断点续传是怎么做的

无线网络随时可能中断，如果每断一次都要从头传一遍固件，体验和成功率都会很差。做法很朴素：

  1. 记录已接收偏移量

    每写入一块，就把"已接收长度"写进参数区或 Flash 元数据里。注意要定期落盘而不是每块都写，否则元数据的擦写次数会飙升。

  2. 中断后带着偏移量重连

    重新连上服务器时，把 offset 报上去。用 HTTP 时就是发 Range: bytes=12345-，服务器返回 206 Partial Content，而不是从头开始。

  3. 校验失败时局部重传

    对分块序号做校验，只重传出错的块，不必推倒重来。这一步在自定义协议里容易做，用 HTTP 时需要"分片下载 + 分片校验"。

  4. 换包要作废偏移量

    如果服务器上的固件包更新了（版本号或哈希变了），之前记录的 offset 必须清零。否则会把新包的数据接在旧包的尾巴后面，得到一个必然校验失败的镜像——这是断点续传最隐蔽的 Bug。

写入与重启的顺序

顺序错了，一次断电就可能变砖。正确的做法是：

① 固件完整写入 Slot B ② 整包 CRC + Hash 校验通过 ③ 验签通过 ④ 更新版本号与升级标志 ⑤ 最后一步：复位重启
判断标准很简单：在第 ⑤ 步之前的任何时刻断电，重启后设备都应该能正常运行旧固件。如果做不到，说明写入顺序或分区设计有问题。

4.6 无线 OTA 的优缺点与适用场景

优点

  • 可远程批量升级，人工成本近乎为零
  • 速率显著高于串口，适合大固件
  • 能与云平台联动，做灰度发布与版本统计
  • 用户侧体验好：App 一键升级、自动升级

缺点

  • 依赖网络与环境，弱网下成功率与体验下降
  • 功耗上升，电池设备需特别设计充电策略
  • 暴露在公网，需要 TLS、签名与鉴权等安全机制
  • 实现链路长：云平台、协议、证书、版本管理都要投入

智能家居

Wi-Fi 设备在用户家中，升级必须"无感"，失败要有兜底。

户外 / 工业设备

4G 或 Wi-Fi 远程升级，避免昂贵的现场作业。

智能穿戴

BLE 升级 + 设备端确认，兼顾低功耗与安全性。

本章小结

  • 三条无线通道的取舍维度：速率、功耗、连接成本、覆盖范围。
  • BLE 4.2 与 BLE 5 的速率差一个数量级，评估方案时不能混为一谈。
  • 协议选型口诀：MQTT 发指令、HTTPS 传固件，别用 MQTT 搬固件。
  • 断点续传必须处理"换包作废偏移量"，否则会出现必然失败的镜像。
  • 写入顺序铁律：数据 → 校验 → 验签 → 标志 → 重启。

自测

  1. 为什么说"用 MQTT 直接传固件"是个坏主意？
    2. 查看答案

    MQTT 长连接在弱网下频繁重连，且缺少 Range 断点续传、CDN 加速与成熟的证书体系；传几 MB 数据成功率极低。正确做法是 MQTT 下发 URL，HTTPS 下载。

  1. 断点续传时服务器上的包换了版本，会发生什么？
    2. 查看答案

    旧偏移量被沿用，新包从中间位置续写，最终镜像前后来自两个不同版本，CRC 必然失败，且用户会看到"反复下载反复失败"。必须在换包时清空 offset。

Chapter 05

进阶技术：差分、压缩与 A/B 实现

前四章讲的是"能用"的 OTA。这一章讲"用得起、用得省"的 OTA：当固件从 500KB 长到 5MB，当设备装在只能 NB-IoT 上报的井盖下，当 Flash 只够放一份固件时，你需要的是这一章的技术。

5.1 差分升级（Delta OTA）

差分升级（也叫增量升级、Delta OTA）只传输"新旧两版之间的差异"，设备端再用旧固件 + 差分包"打补丁"还原出新固件。它解决的问题很直接：整包太大，传不起。

是什么服务器端比较旧固件 A 与新固件 B，生成一个体积远小于 B 的差分包 Δ；设备下载 Δ 后，本地用 A + Δ 重建出 B。
为什么嵌入式固件里大量内容是"改一个 Bug 但整体镜像几乎不变"。实测中，几 MB 的固件做小改动，差分包常常只有原大小的 2%~10%，流量和下载时间能降一个数量级。
怎么工作服务器用 bsdiff 等算法算出 Δ → 设备下载 → 校验 Δ 本身 → 用旧镜像逐块 patch 出新镜像 → 校验新镜像的 Hash → 写入目标分区。

为什么差分包能这么小

固件镜像的字节分布非常"结构化"：常量表、字符串、中断向量、编译产物都成段重复。bsdiff 的思路是后缀排序 + 最长公共子串匹配，把新文件描述成"从旧文件的某处复制一段 + 插入若干新字节"的指令序列。真正需要传输的只是这些指令和新增数据。

算法思路差分包大小设备端内存需求适用
bsdiff / bspatch后缀排序求最长公共子串，生成 copy/add 指令最小（典型 2%~10%）高：经典实现需要约 17× 文件大小的 RAM资源较宽裕、追求极致压缩率
hdiffpatch同上，但做了流式与内存优化与 bsdiff 相当较低，支持流式 patchMCU 上的首选
courgette（Chrome）反汇编后做指令级比较更小高，依赖架构PC / 手机，MCU 上不现实
块级差分按固定块（如 4KB）比对，只传变化的块较大（10%~40%）极低，可流式RAM 极小、实现最简单的场景

差分的四个"坑"

  1. 强依赖基线版本

    差分包只能从"某个确定的旧版本"打到"某个确定的新版本"。设备群里有 10 个历史版本，就要准备 10 个差分包，或者做"版本升级路径图"。版本碎片化是差分升级最大的运维成本。

  2. RAM 放不下经典 bspatch

    MCU 只有几十 KB RAM，跑不了标准 bspatch。解决办法是用 hdiffpatch 的流式模式，或退化成块级差分。设计前先算清楚"patch 需要多少 RAM"。

  3. 旧镜像必须逐字节一致

    patch 时用的是设备上实际存在的旧固件，不是服务器上的旧固件文件。如果设备上的旧镜像被改过（比如出厂时烧的是调试版、或某次升级是"就地覆盖"而非双分区），差分就会失败。因此差分升级通常要求旧固件有已知的 Hash，并在 patch 前先校验。

  4. patch 失败必须有退路

    差分失败（Hash 不匹配、RAM 不足、断电）时，设备应该能退回"下载整包"或"保持旧版本"。别让差分成为唯一路径。

决策建议：固件 < 1MB 且升级不频繁 → 不值得做差分，整包的工程成本低得多。固件 > 2MB、设备数上千、按流量计费（NB-IoT / 蜂窝） → 差分的收益非常明显，值得投入。混合策略最常见：小版本走差分，跨大版本或差分失败时自动回落整包。

5.2 压缩与流式解压

压缩和差分解决的是同一个问题的两个侧面：减少要传的字节数。压缩的优点是实现简单（服务器压一次，设备解一次），缺点是对"已经高度压缩"的镜像效果有限。

算法压缩率（固件镜像）解压 RAM解压速度适合
heatshrink约 30%~50%几十字节慢RAM 极小的 8 位 MCU
LZ4约 45%~60%约 16~64 KB（块模式可更小）极快32 位 MCU 的通用首选
zlib / deflate约 55%~70%约 32 KB（可用 miniz 裁剪）中等Flash 紧张、RAM 尚可
LZMA约 65%~80%大（几十 KB 起）很慢PC / Linux 端，MCU 上少见

流式解压：不要"先解压到 RAM"

新手最常见的错误写法是：把整个固件解压到一块 RAM 缓冲区，再整体写入 Flash。这在 MCU 上几乎必然失败——固件 500KB，RAM 只有 64KB。

正确做法是边解压边写，用固定大小的小缓冲区（如 4KB）循环：

/* 流式解压 + 直接写 Flash 的骨架 */
#define CHUNK   4096

static uint8_t in_buf[CHUNK];
static uint8_t out_buf[CHUNK];

int ota_stream_decompress(uint32_t src_addr, uint32_t dst_addr, uint32_t src_len)
{
    lz4_stream_t ds;
    lz4_init(&ds, out_buf, CHUNK);
    uint32_t written = 0;

    for (uint32_t off = 0; off < src_len; off += CHUNK) {
        uint32_t n = (src_len - off < CHUNK) ? (src_len - off) : CHUNK;
        flash_read(src_addr + off, in_buf, n);

        int produced;
        while ((produced = lz4_decompress_chunk(&ds, in_buf, n)) > 0) {
            if (flash_write(dst_addr + written, out_buf, produced) != 0)
                return OTA_ERR_FLASH_WRITE;
            written += produced;
            wdt_feed();                      /* 解压 + 擦写都很慢，必须喂狗 */
        }
    }
    return (written == expected_size) ? OTA_OK : OTA_ERR_SIZE;
}
三个必须注意的点：① 解压后的长度必须校验——很多解压库在被喂了损坏数据时不会报错，只是"解出更少的数据"，所以要用头部里的 payload_size 做最终比对；② 擦除要提前做，不要和解压交错进行，否则每次擦除都打断解压状态机；③ 压缩率别指望太高——加密过的固件、已经压缩过的资源（图片、字库）再压几乎没有收益，可以只压代码段。

5.3 A/B 分区的三种实现

前面反复提到"双分区"，但双分区具体怎么落地，有三种差别很大的实现方式。选错了会在 Flash 空间和升级耗时上付出代价。

实现方式做法Flash 需求升级耗时典型实现
① 直接写入（copy） 新固件直接下载进"非活动 Slot"，校验通过后只切启动标志，不做任何搬运 2 份固件空间 最短：只有下载 + 校验 ESP-IDF OTA、STM32 双 Bank、多数自研方案
② 交换（swap） 只有 1 个 APP Slot，新固件先写进临时区，再与旧固件整体交换位置 1 份固件 + 1 份临时区 长：要做两次大块搬运 MCUboot 的 swap 模式
③ 交换 + scratch 在 ② 的基础上加一块小 scratch 区做"三路交换"，降低临时区需求 1 份固件 + 小 scratch 最长：块数多，且每块要写三次 MCUboot 的 swap-using-scratch
怎么选：Flash 够 → 一律选 ①直接写入，最简单也最快，升级失败连搬运都不用管。Flash 只够一份半 → 才考虑 swap。注意 ②③ 的共同风险：交换过程本身是"多次擦写"，一旦在交换中途断电，必须依赖 Bootloader 里的"交换状态记录"来继续或回滚，实现复杂度远高于 ①。

三种方式都需要回答同一个问题：什么时候把新固件标记为"确认可用"。答案见 6.1 状态机 与 6.5 回滚。

5.4 版本号规范与版本矩阵

版本号是 OTA 的"身份证"。设计得随意，后期会出现"设备上报的版本号无法判断该不该升级""两个不同固件版本号相同"这类难解的问题。

推荐的版本号结构

主版本.次版本.修订号+构建号，例如 2.4.1+20261124。主版本变化表示不兼容（可能需要新硬件或新协议）；次版本表示新增功能；修订号表示修 Bug。构建号用日期或 CI 序号，保证任何一次构建都可唯一追溯。

别用"版本号大小"直接比大小

字符串比较会得出 "1.10" < "1.9" 这种错误结论。设备端应把版本号打包成单调递增的 32 位整数（如 主<<24 | 次<<16 | 修订<<8 | 构建）再比较，或者干脆另存一个 version_code 字段。

版本矩阵：为什么"有新版本"不等于"该给你升"

真实产品里，一个固件包能否推给某台设备，取决于多个维度的匹配。缺少任何一维都可能造成批量事故：

维度说明不匹配的后果
硬件型号 / 硬件版本同一产品可能有多版 PCB（改了外设、换了 Flash）刷进去后外设初始化失败，设备起不来
区域 / 认证不同国家射频法规、认证要求不同违反当地法规，产品被下架
运营商蜂窝设备的 APN、频段配置不同升级后无法联网，彻底失联
当前版本差分包的基线版本、跨大版本升级路径差分失败，或跨版本升级后配置不兼容
Bootloader 版本新 APP 可能依赖新版 Bootloader 的分区布局APP 跑起来但升级能力失效
发布通道内测 / 灰度 / 全量把测试版推给了全量用户
实践做法：让固件头部携带 hw_id（型号+硬件版本）与 min_bootloader_version，设备端在下载之前就完成匹配；云端再用"设备标签"做二次过滤。双重校验不是冗余，而是防止"云端配置错一次就全军覆没"。

5.5 资源与时间预算

设计 OTA 方案前，先把这三个数字算清楚。算不清楚就开工，后期一定返工。

① Flash 预算

Bootloader + 元数据(双副本) + 2×APP + 文件系统 + 密钥区。若做差分还要额外一块暂存区。经验值：可用 Flash 至少要能装下 2.2 份固件。

② RAM 预算

下载缓冲（4~16KB）+ 解压上下文（LZ4 约 16KB）+ TLS 握手（30~50KB，若用 HTTPS）。TLS 往往是 RAM 的最大消耗项，比 OTA 本身还大。

③ 时间预算

下载时间 = 固件大小 ÷ 有效带宽，再加擦除时间（每 4KB 扇区约 20~100ms）+ 校验时间 + 验签时间。验签在小 MCU 上可能占 1~3 秒，别忽略。

一个具体的算例

环节假设耗时
下载500KB 固件，Wi-Fi 有效 60KB/s≈ 8.3 秒
擦除 Slot B500KB ÷ 4KB = 125 个扇区，每个 40ms≈ 5 秒
写入125 个扇区，每个写入 15ms≈ 1.9 秒
整包 CRC32500KB @ 20MB/s（硬件 CRC 或优化实现）≈ 0.03 秒
SHA-256 + ECDSA 验签Cortex-M4 @ 120MHz，软件实现≈ 0.4 ~ 1.2 秒
合计不含重启与自检≈ 16 秒

可以看到：擦除时间常常比下载还长。优化方向不是"提高带宽"，而是"边下载边擦除"或"减少无谓擦除"（只擦要写的扇区，而不是整片分区）。

本章小结

  • 差分把传输量降到 2%~10%，代价是强依赖基线版本，运维复杂度上升。
  • MCU 上跑不了经典 bspatch，用 hdiffpatch 流式模式或块级差分。
  • 压缩必须"流式解压 + 边解边写"，绝不能先解到 RAM。
  • A/B 三种实现：直接写入最快最简，swap / swap-scratch 是 Flash 妥协方案。
  • 预算三件套：Flash 至少 2.2 份固件、RAM 主要被 TLS 吃掉、时间主要被擦除吃掉。

自测

  1. 什么情况下不该做差分升级？
    2. 查看答案

    固件较小（<1MB）、升级频率低、版本碎片少、流量不敏感时。差分的工程与运维成本高于它省下的流量。

  1. 500KB 固件、4KB 扇区、每扇区擦除 40ms，光擦除要多久？
    2. 查看答案

    125 个扇区 × 40ms = 5 秒。所以"边下载边擦除"往往比"提高下载带宽"更能缩短总时长。

  1. swap 模式相比直接写入，最大的额外风险是什么？
    2. 查看答案

    交换过程需要多次擦写同一批扇区，中途断电会留下"半交换"状态，必须靠 Bootloader 记录交换进度来续做或回滚，实现复杂度和出错面都大得多。

Chapter 06

可靠性工程：让升级"永远回得去"

这一章是全书的核心。前五章解决"能不能升"，这一章解决"升坏了怎么办"。判断标准只有一条：在任何时刻、任何环节断电或崩溃，设备重启后都必须能跑起来。

6.1 升级状态机与元数据

OTA 不是一个"开始 → 成功"的线性过程，而是一个跨多次重启的分布式状态机。设备可能在任意一步断电，下次上电时必须知道"我上次做到哪儿了"。这就是元数据里必须存状态、而不仅是"一个升级标志"的原因。

关键设计：TRIAL → VALID 的"确认"由谁来做

确认方式做法优点缺点
APP 自检后自动确认新固件启动后初始化外设、连上网络、上报心跳，然后写 VALID无需人工，适合无人值守设备"自检"标准要设计好，否则会确认一个"能启动但功能坏了"的固件
用户确认BLE 穿戴设备等用户按键/App 确认后才 VALID最安全，能拦住"功能异常"的固件超时未确认会回滚，用户可能以为"升级失败"
云端确认设备上报"已启动新版本"，云端下发 confirm 指令可在云端做二次判断（如灰度指标）依赖网络；断网设备永远停在 TRIAL
推荐组合："APP 自检自动确认 + 保留云端否决权"。设备启动后完成自检（关键外设可用、能联网、版本号正确）即写 VALID，避免因断网卡在 TRIAL；同时上报状态给云端，若云端发现该版本异常，可下发"回滚指令"触发反向升级。

6.2 断电保护

断电是嵌入式设备最常见也最猝不及防的故障源——你永远无法阻止用户在刷写过程中拔电。设计上要做的是：让断电发生在任何时刻，设备都还能启动。

铁律一：先写数据，最后写标志

升级标志是"提交点"。在写它之前断电，重启后旧固件照常运行；写完它才意味着新固件已就绪。

铁律二：标志写入要原子

标志字段要按对齐的单字写入，写完回读校验；更稳妥的做法是写两份带 seq 的副本（见 2.7），读出时取有效的那份。

铁律三：始终留一条退路

永远保留一份可启动的固件（A/B 分区），或至少保留可用的串口恢复通道。

掉电检测（BOR / PVD）：抢在电压跌落前收手

MCU 一般有掉电检测模块（STM32 叫 PVD，其它厂商叫 LVD / BOR）。它的价值在于：当输入电压跌到阈值以下时产生中断，让你有机会在 Flash 写入尚未完成时"不做无意义的事"——具体做法是：

  • PVD 中断里立即停止发起新的 Flash 写操作，把当前正在写的块写完（Flash 写入一旦开始必须让它完成，中途放弃反而可能损坏该扇区）。
  • 设置一个"紧急标志"，让重启后走"检查并修复"流程，而不是直接跑 APP。
  • 不要在 PVD 中断里做任何耗时操作（打印日志、写元数据），因为电容里剩余的能量只够几十毫秒。
一个现实约束：大多数设备的电源上没有足够大的储能电容，PVD 触发后往往只来得及"停止新操作"，来不及"完成收尾"。所以不能把可靠性寄托在 PVD 上——它只是锦上添花，真正的保障还是"双分区 + 标志最后写 + 双副本元数据"这套结构性设计。

6.3 看门狗与复位原因

看门狗（Watchdog）是"设备卡死后自动复位"的硬件保障。但在 OTA 场景里，它有两个非常容易踩的坑。

坑一：升级过程中被看门狗误杀

擦除一个大扇区可能要几百毫秒，验签可能要一两秒。如果看门狗超时设成 500ms，设备会在升级中途不停复位，表现为"升级永远失败"。解决办法：在擦除、解压、验签的长循环里周期性喂狗，或者升级期间临时切换到更长的超时窗口。

坑二：跳转到 APP 后看门狗没交接

如果 Bootloader 开了看门狗，跳到 APP 后 APP 没有及时重新初始化并喂狗，设备会在 APP 启动几毫秒后复位，形成"复位循环"。解决办法：跳转前要么关掉看门狗，要么确保 APP 启动第一件事就是初始化并喂狗——两者必须约定清楚，不能"各写各的"。

复位原因识别：区分"掉电"与"崩溃"

Bootloader 需要知道"上次为什么重启"，才能决定是否把 boot_attempts 加一。几乎所有 MCU 都有复位标志寄存器（STM32 的 RCC->CSR、ESP32 的 esp_reset_reason()、nRF 的 RESETREAS）。

/* 读取并清除复位原因 —— 注意"读后要清"，否则下次判断会沿用旧标志 */
typedef enum {
    RST_POWER_ON,     /* 正常上电 */
    RST_PIN,          /* 复位引脚 */
    RST_WATCHDOG,     /* 看门狗：多半是 APP 卡死 */
    RST_SOFTWARE,     /* 软件主动复位：OTA 提交后正常重启 */
    RST_BROWNOUT,     /* 掉电/欠压：不要计入"启动失败" */
    RST_UNKNOWN
} reset_reason_t;

reset_reason_t get_and_clear_reset_reason(void)
{
    uint32_t f = RCC->CSR;
    reset_reason_t r = RST_UNKNOWN;

    if (f & RCC_CSR_BORRSTF)      r = RST_BROWNOUT;
    else if (f & RCC_CSR_IWDGRSTF) r = RST_WATCHDOG;
    else if (f & RCC_CSR_SFTRSTF)  r = RST_SOFTWARE;
    else if (f & RCC_CSR_PORRSTF)  r = RST_POWER_ON;

    RCC->CSR |= RCC_CSR_RMVF;      /* 清标志，关键一步 */
    return r;
}
为什么这个判断很重要？如果设备装在电压不稳的现场，每次掉电都会被误判为"新固件启动失败"，几次之后就自动回滚了——用户会看到"设备莫名其妙退回了旧版本"。正确做法是：只有 RST_WATCHDOG 和"APP 未在超时内确认"才计入失败次数，掉电与手动复位不计入。

6.4 升级失败处理与错误码

把升级过程拆开逐个环节排查，会发现失败总是发生在固定的几个位置：

失败环节典型原因设备表现应对措施
下载阶段网络中断、服务器超时、URL 过期下载卡住或反复重试分块下载 + 断点续传 + 超时退出 + 重新申请 URL
写入阶段写入途中掉电、Flash 坏块Flash 内容半新半旧固件先写、标志最后写；写非活动分区；写入后回读比对
校验阶段数据传输损坏、固件被截断校验失败分块校验 + 整包校验，失败即丢弃并记录错误码
启动阶段新固件有 Bug 或配置错误反复重启、进不了 APP看门狗复位 + 启动失败计数 + 自动回滚
版本阶段固件与硬件型号不匹配启动即异常、功能异常头部 hw_id 校验 + 灰度发布验证
安全阶段固件未签名或签名不合法拒绝写入或拒绝启动公钥验签 + 安全启动

错误码体系：让"升级失败"变成一句可诊断的话

"升级失败了"这五个字对排障毫无帮助。正确做法是定义一套分段错误码：高位表示阶段，低位表示具体原因。设备上报给云端，售后看一眼就知道该查哪里。

/* 错误码 = 阶段(高 8 位) | 原因(低 8 位) */
#define OTA_ERR(stage, reason)   (((stage) << 8) | ((reason) & 0xFF))

#define ST_DOWNLOAD  0x01
#define ST_VERIFY    0x02
#define ST_FLASH     0x03
#define ST_BOOT      0x04
#define ST_SECURITY  0x05

typedef enum {
    OTA_OK                   = 0,

    OTA_ERR_NET_TIMEOUT      = OTA_ERR(ST_DOWNLOAD, 0x01), /* 网络超时 */
    OTA_ERR_HTTP_STATUS      = OTA_ERR(ST_DOWNLOAD, 0x02), /* 服务器返回 4xx/5xx */
    OTA_ERR_URL_EXPIRED      = OTA_ERR(ST_DOWNLOAD, 0x03), /* 预签名 URL 过期 */
    OTA_ERR_SIZE_MISMATCH    = OTA_ERR(ST_DOWNLOAD, 0x04), /* 收到的长度与头部不符 */

    OTA_ERR_CRC              = OTA_ERR(ST_VERIFY,   0x01), /* 整包 CRC 不匹配 */
    OTA_ERR_HASH             = OTA_ERR(ST_VERIFY,   0x02), /* SHA-256 不匹配 */
    OTA_ERR_SIGN             = OTA_ERR(ST_VERIFY,   0x03), /* 签名验证失败 */
    OTA_ERR_HW_ID            = OTA_ERR(ST_VERIFY,   0x04), /* 硬件型号不匹配 */
    OTA_ERR_DOWNGRADE        = OTA_ERR(ST_VERIFY,   0x05), /* 版本低于当前，被拒绝 */

    OTA_ERR_FLASH_ERASE      = OTA_ERR(ST_FLASH,    0x01), /* 擦除失败 */
    OTA_ERR_FLASH_WRITE      = OTA_ERR(ST_FLASH,    0x02), /* 写入失败 */
    OTA_ERR_FLASH_VERIFY     = OTA_ERR(ST_FLASH,    0x03), /* 回读比对失败 */
    OTA_ERR_NO_SPACE         = OTA_ERR(ST_FLASH,    0x04), /* 分区空间不足 */

    OTA_ERR_BOOT_TIMEOUT     = OTA_ERR(ST_BOOT,     0x01), /* 新固件未按时确认 */
    OTA_ERR_BOOT_CRASH       = OTA_ERR(ST_BOOT,     0x02), /* 新固件启动即崩溃 */
    OTA_ERR_NO_VALID_SLOT    = OTA_ERR(ST_BOOT,     0x03), /* 两个分区都不可用 */

    OTA_ERR_PUBKEY           = OTA_ERR(ST_SECURITY, 0x01), /* 公钥无效/缺失 */
    OTA_ERR_TLS              = OTA_ERR(ST_SECURITY, 0x02), /* TLS 握手失败 */
    OTA_ERR_CERT_EXPIRED     = OTA_ERR(ST_SECURITY, 0x03)  /* 证书过期（设备时间错误） */
} ota_err_t;
落地要点：① 错误码要持久化到元数据里，因为很多错误发生在重启前后，只存 RAM 会丢；② 上报时带上"失败时的进度百分比"，能立刻区分"完全没开始"和"传到 90% 才断"；③ 附录 C 给了一份完整的错误码对照表，可直接作为排障手册使用。

6.5 固件回滚（Rollback）

回滚指设备升级到新版本后出问题，自动或手动退回到上一版本。没有回滚的 OTA 是不完整的——一次错误推送可能让上万台设备同时失去功能。

回滚方式触发者特点
Bootloader 自动回滚设备自身（启动失败计数超阈值）最可靠，不依赖网络；需要 A/B 分区支持
云端回滚服务器下发旧版本用于"新版本本身有严重 Bug"的场景；依赖网络，且要求旧版本仍可被推送
应用层回滚APP 自己检测到异常如新版本功能异常时主动降级，需要业务逻辑配合
人工回滚售后工程师通过串口/BLE 工具兜底手段，适合设备已失联的情况
注意区分："防降级计数"不是回滚方式，而是安全机制——它阻止攻击者刷入有漏洞的旧版本。它与"可回滚"是一对天然矛盾，见 6.6。

6.6 防降级与可回滚的冲突

这是一个几乎每份 OTA 设计文档都会漏掉、但安全评审一定会问的问题：

矛盾：为了安全，必须拒绝降级——否则攻击者可以把设备刷回有已知漏洞的旧固件，再实施攻击。为了可靠，又必须支持回滚——否则新版本有 Bug 时设备无法自救。
如果简单地"拒绝任何版本号更低或相等的固件"，自动回滚就会被自己的安全策略挡住。

工业界的解法：单调计数器 + 授权回滚

单调安全计数器（Monotonic Counter）

设备内维护一个只增不减的 security_version（存在 OTP/eFuse 或受保护 Flash）。固件头部携带 min_security_version，Bootloader 要求它 ≥ 当前计数器。回滚时不是"降低版本号"，而是"换一个仍然满足安全等级的旧版本"——只要那个旧版本的安全等级足够，就允许启动。

授权回滚版本表（Rollback Allow List）

厂商在签名固件时，同时签一份"允许回滚到的版本白名单"，随固件一起下发并存入元数据。Bootloader 在回滚前检查目标版本是否在白名单里。这样回滚能力由厂商的签名授权控制，而不是由版本号大小控制。

实践中的组合策略

  1. 区分"正常升级"与"回滚"两条路径

    正常升级要求 version > current；回滚路径不比较版本，只校验"目标镜像的签名 + 是否在白名单 + 安全计数器是否满足"。

  2. 回滚路径只能由本地状态机触发

    回滚不接受云端任意下发（否则云端被攻破就等于降级攻击入口）。云端只能"建议回滚"，最终由设备的启动失败计数与白名单决定。

  3. 安全计数器只在"必须"时递增

    递增后旧版本就永久不可回滚。所以它只在"发现严重漏洞、必须强制淘汰旧版本"时使用，日常升级不要动它。

  4. 记录完整的版本历史

    元数据里保存"曾运行过的版本 + 时间 + 结果"，既便于排障，也能在审计时证明"设备从未运行过低于某安全等级的固件"。

本章小结

  • OTA 是跨重启的状态机，元数据必须持久化"状态 + 计数 + 错误码"。
  • TRIAL → VALID 的确认机制是自动回滚的前提，推荐"自检自动确认 + 云端否决权"。
  • 断电保护靠结构设计（双分区 + 标志最后写 + 双副本），不靠 PVD。
  • 必须区分复位原因：只有看门狗/超时未确认才计入失败，掉电不算。
  • 防降级与可回滚的矛盾，用"单调计数器 + 授权回滚白名单"化解。

Chapter 07

安全机制：只允许升级可信固件

OTA 是一把双刃剑：它让你能远程修 Bug，也让攻击者多了一条远程改写设备的通道。这一章讲清楚"校验、签名、信任链、密钥、加密、通道"六件事，以及它们在 MCU 上的现实约束。

7.1 固件完整性校验：CRC、Checksum 与 Hash

完整性校验解决的是"固件在传输和存储过程中有没有被损坏"。常见的三种手段强度依次递增：

Checksum 校验和

把所有字节加起来取反或取模。最简单，实现成本几乎为零，但检错能力很弱，几比特出错就可能看不出来。

CRC 循环冗余校验

按位运算生成一个固定长度的"指纹"（常见 CRC-16 / CRC-32）。能可靠发现突发错误，是串口协议与 Flash 校验的事实标准。

Hash 摘要

SHA-256 等算法生成固定长度摘要，任何一个比特改变都会让摘要完全不同。用于整包校验和签名输入。

方法能发现什么不能发现什么典型用途
Checksum少量比特错误复杂错误模式简单协议的快速自检
CRC-16 / CRC-32传输与存储中绝大多数错误人为篡改分块传输校验、Flash 读回校验
SHA-256任何比特的变化攻击者重算摘要后的替换整包校验、签名输入
关键区别：CRC 和 Hash 都是"公开算法"，攻击者拿到固件包后可以重新算一遍校验值，把篡改后的固件伪装成合法的。所以它们只能防"意外损坏"，防不了"恶意篡改"——后者要靠数字签名。

补充一点实现经验：CRC 参数（多项式、初值、是否反射、结果异或）必须两端一致，否则会出现"我这边算出来永远不对"的低级故障。推荐直接用 CRC-32/ISO-HDLC（即 zlib 用的那套），工具链与库都现成。

7.2 固件身份验证与数字签名

数字签名解决的是"这个固件到底是谁发布的"。它基于非对称加密：厂商用只有自己持有的私钥对固件签名，设备里预置对应的公钥，设备用公钥验证签名是否成立。

验签到底应该在哪一步做？

这是本书前几版里最容易写乱的地方，这里一次说清楚。设备端只有三种可行做法，各有代价：

做法流程能否保证"不可信固件一个字节都没进 Flash"适用
先收到 RAM 再验签 整个包放 RAM → 验签 → 通过才写 Flash 能 仅小固件（RAM 要能装下整包）
边收边写 + 收完验签（推荐） 逐块写进非活动分区并累计 Hash → 收完用公钥验签 → 通过才提交启动标志 不能（不可信数据确实进过 Flash，但永远不会被启动） 绝大多数 MCU 方案
边收边写 + 边验签 流式签名验证（如 RSA 的流式模式），每块到达即参与运算 能，但实现复杂，算法受限 对安全性要求极高且资源足够
结论与话术统一：本书采用第二种。它的安全边界是——"不可信固件可以落进非活动分区，但永远不会被提交、永远不会被启动"。这已经足够：攻击者能写进去的东西，等于写进一个被 Bootloader 拒绝的垃圾区。
但要记住代价：非活动分区在被写入期间是"脏"的，如果此时断电，该分区处于半新半旧状态——所以必须先把它标记为无效，再开始写，不能等写完才标记。

安全启动（Secure Boot）

把验签提前到启动链最前端：Bootloader 一上电就先验 APP 的签名，不通过就拒绝启动。这样即使攻击者用编程器写入了固件，设备也跑不起来。安全启动与 OTA 是同一套密码学基础的两种用法——OTA 验签决定"能不能装"，安全启动决定"能不能跑"。

设备身份与双向认证

设备出厂时烧入唯一证书（设备私钥放安全芯片或受保护区域），与服务器建立 TLS 双向认证。设备认证解决"谁在下载"，固件验签解决"下载的是什么可信"，两者都要有。

7.3 信任根与密钥管理

签名机制的安全性最终取决于一件事：设备里的那把公钥从哪来、会不会被换掉。这个"不可再被追问的起点"就是信任根（Root of Trust）。

密钥管理：从产线到吊销

环节要解决的问题推荐做法
生成私钥不能泄露、不能只有一个人掌握在 HSM（硬件安全模块）中生成，私钥永不出 HSM；多人分权审批才能签名
注入产线上每台设备要有唯一身份产线工具从云端拉取"一次性证书"，烧完即作废；注入过程记入审计日志
存储设备端私钥可被读走放安全芯片 / TrustZone / 受读保护的区域；绝不放普通 Flash
使用签名操作被滥用签名服务只接受"已通过测试的固件"，自动加版本号与时间戳，人工无法绕过
轮换密钥可能泄露，需要换新固件头部支持多公钥槽（如 3 个），新固件同时被新旧密钥签名；等全量升级完成后再淘汰旧密钥
吊销某把私钥确认泄露云端停止用该密钥签名 + 下发"吊销列表"固件，把该公钥槽标记为失效
最容易被忽略的一条：多公钥槽。如果设备里只有一个固定公钥，一旦私钥泄露，全网设备都无法通过 OTA 自救——因为要换公钥就必须升级固件，而升级固件又要用那把已泄露的私钥签名。这是"密钥设计不留后路"的经典死局。留 2~3 个槽位，成本几乎为零，价值极高。

7.4 固件加密与调试口保护

很多人以为"有签名就安全了"。但如果攻击者能直接用调试器把 Flash 读出来，前面所有验签工作都白做——他拿到的是明文固件，可以逆向、找漏洞、甚至提取业务密钥。签名防的是"改"，加密与读保护防的是"看"。

调试口保护（第一优先级）

出厂前关闭或锁定 SWD/JTAG：STM32 的 RDP Level 1/2、nRF 的 APPROTECT、ESP32 的 FLASH_ENCRYPTION + 安全启动。这一步不做，其它安全措施基本无效。注意：RDP Level 2 是不可逆的，量产前务必确认。

固件加密

用 AES-128/256 加密镜像，密钥存在芯片的密钥区（不可读）或由 OTP 派生。Bootloader 边解密边写入目标分区。注意：加密不替代签名——加密防"看"，签名防"改"，两者要同时做（先签名后加密，设备端先解密再验签）。

安全启动 + 防回滚

配合 6.6 的单调计数器，构成完整链条：读不出（调试口锁定）→ 改不了（签名）→ 跑不了旧版（防降级）。

一个现实权衡：加密会让"边收边写"变成"边收边解密边写"，CPU 开销上升，且解密上下文需要额外 RAM。如果芯片本身有 Flash 硬件加密（如 ESP32 的 flash encryption、STM32 的部分型号），优先用它而不是自己写 AES 软件实现——自研密码实现是漏洞的高发区。

7.5 通道安全与设备身份

固件本身可信，还要保证"它是从正确的服务器、传给正确的设备"。这靠三层机制叠加：

① 传输加密（TLS）

防止中间人窃听与篡改。注意：TLS 保护的是"这一条链路"，如果服务器本身被攻破，TLS 帮不了你——所以还要有固件签名。

② 设备鉴权

防止"任何一台设备都能下载任意固件"。常用方式：设备证书（mTLS）、预共享密钥、动态 token。推荐 mTLS + 云端按设备标签授权。

③ 下载地址防扩散

固件 URL 用预签名、短时效的地址（如 15 分钟有效），并且绑定设备 ID 或 IP 段。避免固件包被爬走、被刷流量。

常见误区："我们用了 HTTPS，所以安全了。"——HTTPS 只能保证链路安全。攻击者完全可以：① 攻破你的固件服务器，替换成自己的包（HTTPS 依然"成功"）；② 让设备连到自己的假服务器（如果设备不校验证书链或存在自签名信任）。所以固件签名是最后一道、也是唯一一道不依赖基础设施的防线。

7.6 MCU 上 TLS 的现实约束

这一节专门讲"教科书上不说、但一定会卡住你"的问题。很多团队在 PC 上跑通了 HTTPS 下载，移到 MCU 上才发现根本跑不起来。

约束具体表现应对
RAM 占用 TLS 1.2/1.3 握手峰值常需 30~50KB（含证书链解析、密钥协商缓冲）。M0/M3 只有 20~64KB RAM 时非常紧张，且握手期间不能同时做别的内存分配 用 mbedTLS 的 MBEDTLS_SSL_IN_CONTENT_LEN 裁剪；用会话复用（session resumption）跳过完整握手；把 OTA 下载放到"内存最空闲"的时机
证书有效期校验 设备没有 RTC，上电时间可能是 1970 年，导致"证书未生效"或"已过期"而握手失败 ① 用 SNTP 先对时；② 首次启动时通过服务器获取时间；③ 无 RTC 且无法对时时，改用"固定根证书 + 不校验证书时间"（安全性下降，需评估）；④ 使用较长有效期的专用证书
根证书更新 根证书过期后，所有旧设备都连不上，且无法通过 OTA 更新根证书（因为连不上） 设备端预置多个根证书；或预置一个自有 CA 的根证书，由自有 CA 签发服务器证书，这样轮换服务器证书不需要动设备
握手耗时 软件实现的 ECDHE + AES 在 120MHz M4 上握手可能要 1~3 秒，期间看门狗要喂 启用硬件加密加速（CRYPTO/HASH 外设）；用 PSK 或 session ticket 减少非对称运算
代码体积 mbedTLS 完整配置可占 60~100KB Flash，对 256KB Flash 的设备不可接受 裁剪到只用 TLS 1.2 + ECDHE-ECDSA-AES128-GCM-SHA256 一种套件；或用 TLS 1.3 的精简实现（如 wolfSSL、Mbed TLS 3.x 的 tls13 子集）
一句实话：在 64KB RAM 以下的 MCU 上做"完整 TLS + 签名 + A/B 分区"，往往需要大幅取舍。可选路径是：降低 TLS 强度（PSK）、改用 MQTT over TLS 的长连接只传小数据、或引入一颗带 TLS 卸载的 Wi-Fi/蜂窝模组（把 HTTPS 交给模组做，MCU 只通过串口收明文）。后者在工业产品里非常常见。

7.8 五道防线

把前面各节的要点浓缩成一条五道防线，一道都不能少。注意：它们的执行时序与校验强度并不是同一件事，下面分开说明。

  1. 第一道：型号与版本匹配

    固件头部携带 magic 值、硬件型号、固件大小、目标版本。设备先比对，不匹配直接丢弃——避免把 A 型号的固件刷进 B 型号。成本最低，应放在最前面（只需读几十字节头部）。

  2. 第二道：版本合法性检查

    拒绝比当前版本更低的固件（防止降级攻击），并配合服务器灰度名单控制谁能收到哪个版本。注意：回滚路径不走这道，走 6.6 的授权白名单。

  3. 第三道：完整性校验

    分块 CRC 保证传输不坏，整包 CRC / SHA-256 保证落盘不坏。计算量与数据量成正比，必须在写入过程中同步累计，而不是事后重读整片 Flash（重读会多花一倍时间）。

  4. 第四道：数字签名验签

    用设备内置公钥验证厂商签名。验签在"收完之后、提交标志之前"执行，不通过则把目标分区标记为无效，绝不提交启动标志；配合安全启动，连"已经被写坏"也不允许启动。

  5. 第五道：通道安全与身份认证

    下载走 TLS 加密，设备用出厂证书完成双向认证，避免被劫持到假服务器。注意：这道防线发生在最前面（下载一开始就要握手），它和上面四道的时序不同——上面是"对固件做检查"，它是"对链路做保护"。

把五道防线记成一句话："确认身份 → 确认版本 → 确认完整 → 确认可信 → 确认来源"。
执行顺序的原则是"越便宜越靠前"：读头部（微秒级）→ 比版本（微秒级）→ 算 CRC/Hash（毫秒级）→ 验签（百毫秒到秒级）→ 而 TLS 握手与设备鉴权发生在下载开始之前，属于"前置条件"而非"固件检查"。这样能在早期就丢弃明显不合法的包，省电省流量。

7.9 法规与合规

OTA 正在从"开发者的便利工具"变成"产品的法律义务"。如果你做的是出口产品、车载产品或医疗设备，下面这些名字迟早会出现在需求文档里。

法规 / 标准适用与 OTA 的关系
EU CRA（Cyber Resilience Act）在欧盟销售的含数字元素产品强制要求"安全更新能力"与"漏洞披露流程"，主要义务自 2027 年起适用。产品必须能持续接收安全更新，且更新过程不能被降级利用
UN R156（Software Update Management System）车载（M1/N1 等）要求厂商建立 SUMS 体系：软件版本可追溯、更新前后完整性校验、更新失败可恢复、向监管机构报备
ISO 24089道路车辆软件更新工程R156 的工程落地标准，规定了更新流程、记录保存与风险评估
ISO/SAE 21434车载网络安全要求对 OTA 通道做 TARA（威胁分析与风险评估），与 7.7 的矩阵思路一致
IEC 62304 / FDA 预市场指南医疗器械固件更新属于"软件变更"，需要变更控制、验证记录与可追溯性；部分器械的 OTA 需重新申报
IEC 62443工业自动化对设备完整性与补丁管理提出要求，OTA 是满足"补丁管理"条款的主要手段
一个提醒：ISO 26262 是功能安全标准，它约束的是"系统失效不能伤人"，并不直接规定 OTA 怎么做。把 OTA 合规需求挂在 26262 名下是常见的混淆——真正对应的是 R156 / ISO 24089（软件更新）与 ISO/SAE 21434（网络安全）。

本章小结

  • CRC/Hash 防"坏"，签名防"改"，加密防"看"，调试口锁定防"读"，四者分工不同。
  • 验签的可行时机是"边收边写 + 收完验签 + 通过才提交标志"，并明确它的安全边界。
  • 信任根必须放在改不了的地方；公钥要留 2~3 个槽位，否则私钥泄露即全网死局。
  • MCU 上 TLS 的真实瓶颈是 RAM（30~50KB）、时间校验与根证书轮换。
  • 合规要看 CRA / R156 / ISO 24089 / 21434，而不是 ISO 26262。

    2. 查看答案

    HTTPS 只保护链路。服务器被攻破、或设备连到假服务器（证书校验不严）时，HTTPS 依然"成功"。只有固件签名不依赖基础设施。

    设备时间停留在 1970 年，证书被判为"尚未生效"而握手失败。需要 SNTP 对时、服务器授时，或使用不校验证书时间的降级方案。

Chapter 08

OTA 云平台与发布运维

设备端的 OTA 只是"执行器"。真正决定一次升级是"顺利"还是"事故"的，往往是云端的发布策略。这一章讲清楚平台架构、状态一致性、下载链路、灰度与撤包、可观测性这五件事。

8.1 OTA 平台架构

一个够用的 OTA 平台至少包含五个部分。规模小时可以合并部署，但职责边界必须清晰，否则后期会变成一坨无法修改的脚本。

固件仓库的三条铁律

  • 不可变：一个版本号对应一个字节级不变的包，禁止"重新上传覆盖"。否则设备端缓存、差分基线、审计记录全部失效。
  • 可追溯：每个包记录"谁构建、谁签名、谁审批、何时发布"，能对应到具体的 Git commit。
  • 可回取：历史版本不能删（至少保留 N 个），因为回滚要用、差分基线要用。

设备档案要存什么

  • 设备 ID、型号、硬件版本、当前固件版本
  • 分组标签（区域、批次、客户、发布通道）
  • 最近一次升级任务 ID 与结果
  • 最后一次在线时间、上报 IP/网络类型
  • 累计失败次数、最近错误码（用于自动熔断）

8.2 任务状态机与幂等

设备端有状态机（6.1），云端也必须有一份，并且两者要能对齐。否则会出现最常见的运维噩梦："设备明明升级成功了，云端还显示进行中，于是又推了一次"。

幂等的三条设计原则

  1. 任务 ID 全局唯一且随固件包绑定

    设备收到同一个 task_id 的重复通知，应该直接忽略，而不是重新下载一遍。设备端要持久化"已处理过的 task_id"，至少保留最近若干个。

  2. 状态只允许单向推进，且"成功"由设备确认

    云端不能根据"下载请求已返回 200"就判定成功。必须以设备上报的"新版本已运行"为准。中间状态允许"落后"，不允许"超前"。

  3. 重试要有退避与上限

    失败后按 1min → 5min → 30min → 2h 指数退避重试，并设总次数上限。无上限重试会把服务器和设备的电量一起耗光，还会掩盖真实故障。

一个具体的坑：设备升级成功后立刻重启，如果它在"上报成功"之前就断网了，云端会认为任务未完成而重推。下次设备上线时收到的还是同一个任务——此时设备端如果只比较"任务 ID"就会重复下载。解决办法：设备端同时比较"当前版本号"，若已经等于目标版本则直接上报 SUCCESS，不再下载。

8.3 下载链路设计

十万台设备同时下载，和十台设备同时下载，是完全不同的问题。下载链路设计的核心是把压力从自己的服务器转移出去，并把并发削平。

预签名 URL

设备不直接访问固件服务器，而是先向业务服务申请一个带签名、短时效的地址（如 15 分钟），直接从对象存储/CDN 下载。好处：业务服务器不承担流量；URL 泄露后很快失效。

CDN 与就近接入

固件包是"一次上传、海量读取"的典型场景，CDN 命中率极高。注意把 Cache-Control 设为长缓存（因为版本不可变），并保证撤包时能快速失效。

错峰与限速

不要"一键全量推送"。按批次分批唤醒，并在任务里配置每秒下发数上限。否则设备会在同一秒集体上线，把接入层打挂——这类事故在真实项目里非常常见。

设计点做法不做的后果
断点续传支持 HTTP Range；设备持久化 offset 与包哈希弱网下反复从头下载，成功率低、流量翻倍
并发限流接入层按设备维度限速；下载层用 CDN 吸收一次推送打满出口带宽，影响其它业务
失败重定向提供备用下载域名/地域单一 CDN 故障导致全国升级失败
流量成本控制差分优先、非 Wi-Fi 环境提示用户、夜间升级蜂窝流量账单失控（尤其 NB-IoT / 4G 按流量计费）
下载校验设备端校验 Content-Length 与包哈希CDN 返回错误页（HTML）也会被当成固件写入
一个真实事故模式：CDN 在异常时可能返回一个 HTML 错误页，HTTP 状态码却是 200。如果设备只看状态码、不看长度和哈希，就会把几百字节的 HTML 当成固件写进 Flash，校验失败后不断重试。务必先比对 Content-Length 与头部里的 payload_size。

8.4 灰度发布与撤包

灰度发布是把"一次全量"拆成"多次小批量"，用可控的爆炸半径换取发现问题的时间。它是 OTA 运维里投入产出比最高的一件事。

撤包之后，已经升上去的设备怎么办

这是最容易被忽略的决策题。撤包只能阻止"还没升级的设备"，对已升级的设备无能为力。三种处理方式：

策略做法适用风险
反向推送旧版本把上一个稳定版本作为"新版本"重新发布（版本号必须递增，如 1.3.1 → 1.3.2 的修复版，而不是退回 1.2.0）问题严重、必须立即回退若启用了防降级，旧版本号会被拒绝；需走"授权回滚"路径
等下一个修复版不做动作，尽快发修复版本问题不致命、影响面可控用户要多忍受一个版本周期
定向补救只对受影响的设备子集推送修复版问题与特定硬件/区域相关需要准确的设备画像与标签
一条重要经验：永远发布"版本号递增"的包，即使是回退。把 1.3.0 的代码重新打成 1.3.1 发布，比"把版本号改回 1.2.9"要安全得多——后者会与防降级机制冲突，也会让设备端的版本历史出现分叉。

8.5 可观测性与指标

"升级进行中，一切正常"这句话如果没有数据支撑，就是自我安慰。一次发布是否健康，看下面这几个指标就够了。

  • 平台五件套：接入层、设备与版本库、任务编排、固件仓库、签名服务；监控与告警是横向能力。

Chapter 09

测试、量产与成本

"我们测试过了，能升级"——这句话在量产前毫无意义。真正能说明问题的是：在每一个可能的失败点上，我们都试过让它失败，并且它都活下来了。

9.1 异常注入测试矩阵

OTA 的测试不是"跑通一次"，而是系统地制造失败。下面这张矩阵是投入产出比最高的测试资产，建议直接作为测试用例表。

关于断电测试的一个提醒："每个进度点各断电 10 次"听起来很多，但真正的边界往往出现在擦除完成与写入开始的瞬间、以及标志写入的半个字节。建议对这两个时刻额外做 100 次以上的重复测试——它们是"变砖"最集中的地方。

9.2 长稳测试与寿命评估

单次升级通过，不代表连续升级一千次也通过。长稳测试关注的是累积效应：Flash 磨损、内存泄漏、状态残留、计数器溢出。

循环升级测试

让设备在 A/B 之间来回升级 500~1000 次，每次校验功能是否正常。观察点：升级耗时是否逐次变长（内存泄漏/Flash 碎片）、元数据 seq 是否溢出、两个分区是否都被正确擦写。

Flash 寿命评估

算清楚每个扇区每年被擦多少次：升级次数/年 × 每次擦写该扇区的次数。例如每天升级一次、每次擦 2 个扇区，一年约 730 次，对 1 万次寿命的片内 Flash 约占 7%。元数据扇区是消耗最快的，必须做双副本轮换。

RAM / 栈水位

升级流程会引入 TLS、解压、验签等大块内存使用者。用 uxTaskGetStackHighWaterMark 或填魔数法测栈峰值，并留 30% 余量。很多"偶发崩溃"其实是升级路径上的栈溢出。

长稳测试的最小可行方案：一台设备 + 一个自动化的上位机脚本 + 一个继电器控制电源，跑一整周。成本几百块，能发现绝大多数只在"第 300 次升级"才暴露的问题。

9.3 量产落地

产线的 OTA 与售后的 OTA 是两个不同的工程问题：产线追求吞吐与一致性，售后追求可达性与安全。

环节做法关键指标

9.4 成本与预算模型

OTA 不是"免费"的。下面这张表把成本拆成四类，便于在方案评审时把账算清楚——尤其是蜂窝设备，流量账单可能远超硬件成本。

10.3 不同设备应该如何选择

用四个问题就能定位到合适的方案：

Q1 设备规模和位置？

几十台且在实验室 → 串口足够。上千台且分布在现场 → 必须无线。

Q2 设备有什么联网能力？

没有联网能力 → 只能串口。有 Wi-Fi → 首选 Wi-Fi OTA；只有 BLE → BLE DFU + 手机 App；只有蜂窝 → 4G OTA + 差分。

Q3 固件多大、能接受多长时间？

固件 < 200KB 且能接受几十秒 → BLE 4.2 也可以。固件 > 1MB → 必须 Wi-Fi 或高速串口，蜂窝建议配差分。

Q4 安全要求有多高？

涉及支付、门锁、医疗 → 必须签名 + 安全启动 + 加密 + 锁定调试口。物理可接触的场景也不能省签名，因为设备可能被盗用或改装。

工业界的常见组合

产线：串口

一拖多并行烧录，追求节拍与一致性。产线不需要"远程"，需要的是"快且不犯错"。

售后：无线

Wi-Fi / 4G 远程升级，配合灰度与自动回滚。这是 OTA 价值的真正体现。

兜底：串口恢复模式

无线升级彻底失败、设备失联时，保留一条"按键进入 + 串口刷写"的恢复通道。所有量产设备都应该有这条路。

一句选型结论：不要二选一。产线用串口保证一致性，售后用无线保证可达性，串口恢复模式保证兜底——三者共存才是成熟产品的做法。真正需要取舍的只是"售后主通道用 Wi-Fi 还是 4G"，而这取决于设备有没有路由器可用。

本章小结

  • 串口胜在可靠、简单、零网络依赖；无线胜在规模与可达性。
  • 速率上 Wi-Fi > 高速串口 ≈ 4G > BLE 5 > BLE 4.2，差一个数量级。
  • 选型四问：规模、联网能力、固件大小、安全要求。
  • 成熟产品是"产线串口 + 售后无线 + 串口恢复"三通道并存。

自测

  1. 为什么所有量产设备都应保留串口恢复通道？
    2. 查看答案

    因为无线升级依赖网络、云端、证书等多重外部条件，任一环节长期失效都会让设备无法自救。物理可达的恢复通道是最后的保险。

Chapter 11

实际应用与学习路线

最后一章把知识落到"下一步该做什么"。先看真实产品怎么用 OTA，再看需要补哪些前置知识，最后给出一个可以照着走的学习顺序和六个动手实验。

11.1 OTA 在真实产品中的应用

智能家居

Wi-Fi 设备在用户家中，升级必须"无感"：夜间自动下载、用户不操作也能完成，失败时静默回滚。典型约束是不能让用户感知到设备变慢或断连。

物联网设备

电表、水表、井盖传感器，靠 NB-IoT / 4G 上报。固件小、带宽窄、按流量计费，差分升级与错峰推送是刚需。

智能穿戴

手环、耳机通过 BLE 由手机 App 转发固件。设备屏幕小、无法展示细节，因此常要求升级完成后由用户确认，超时自动回滚。

工业与车载

工业网关要求升级期间不影响产线运行（可能要"停机窗口"）；车载受 UN R156 / ISO 24089 约束，需要版本可追溯、更新失败可恢复、向监管报备。

医疗与安防

医疗设备固件更新属于"软件变更"，需要变更控制与验证记录（IEC 62304）；安防摄像头则更关注固件不被篡改与调试口保护。

消费电子外设

键盘、鼠标、TWS 耳机，通过手机 App 走 BLE 升级。特点是量大、单价低、返修不划算，因此对"绝不砖"的要求最高。

11.2 初学者需要掌握的前置知识

必备基础

  • C 语言：指针、结构体、位操作、函数指针
  • MCU 启动流程：复位向量、向量表、栈
  • Flash 特性：扇区、擦写、寿命、读改写限制
  • 串口通信：波特率、帧格式、校验
  • 基本校验算法：CRC 的计算与实现

开始做 OTA 前

  • 能看懂链接脚本（.ld / .icf）与 map 文件
  • 会用调试器查看内存与寄存器
  • 理解中断向量表重定位（SCB->VTOR）
  • 知道看门狗怎么用、怎么喂
  • 会用串口工具与逻辑分析仪抓数据

做量产级 OTA 时

  • 非对称加密与签名验签的基本概念
  • TLS 握手流程与证书链
  • Flash 分区设计与磨损均衡
  • 状态机设计与持久化
  • 基本的云端接口设计与灰度思维

11.3 从串口到无线：推荐的学习顺序

  1. 先读懂自己手上的板子

    打开它的链接脚本与启动文件，找到 Flash 起始地址、向量表位置、栈顶定义。这一步做完，你就理解了"程序是怎么被启动的"。

  2. 用现成工具完成一次串口烧录

    不写代码，先用 STM32CubeProgrammer / esptool 烧一次固件。观察它做了什么、为什么需要"进入下载模式"。

  3. 改造 Bootloader，加入升级协议

    实现最小的"接收 → 校验 → 写入 → 跳转"闭环。先不做双分区、不做签名，把主线跑通。

  4. 补齐校验、标志与失败处理

    加入整包 CRC、升级标志、失败重试上限、错误码。这一步会让你的方案从"能跑"变成"敢用"。

  5. 引入 A/B 双分区

    把 Flash 划成两个 Slot，实现"升级失败自动回到旧版本"。做完这一步，你对 OTA 的理解就超过了大多数人。

  6. 补上安全：验签与调试口保护

    加入公钥验签，锁定调试口。这一步做完，方案才具备量产资格。

  7. 最后接入无线与云端

    把"串口传数据"换成"Wi-Fi 下载数据"，补上 TLS、断点续传、灰度与监控。

为什么无线要放在最后？因为无线带来的复杂度主要在网络与安全，而 OTA 的可靠性内核（分区、校验、标志、回滚）与通道无关。先把内核做扎实，再换通道，事半功倍；反过来则容易做出"能升但一断电就砖"的半成品。

11.4 初学者可以尝试的入门实验

EXPERIMENT 01

让串口"说 hello"

写一段最小代码：上电后通过 UART 打印版本号和剩余 Flash 容量。这是后续所有升级日志、调试信息的基础。

EXPERIMENT 02

手写一次 Flash 擦写

擦除一个扇区、写入一段已知数据、再读出来逐字节比对。亲手体会"擦除后才能写入"这条规则。

EXPERIMENT 03

实现 CRC32 并验证

实现一个 CRC32 函数，故意改动固件里的一个字节，确认校验值发生变化、升级流程能拦截它。

EXPERIMENT 04

在写入中途强制断电

用可编程电源在写 Flash 过程中切断供电，然后上电观察设备是否仍能启动。这是验证"断电保护"设计是否真的有效的唯一方法。

EXPERIMENT 05

把"新固件"故意写坏

让新固件启动后立刻死循环，观察看门狗复位、失败计数增加、自动回滚到旧版本的全过程。

EXPERIMENT 06

接入一次真实的 OTA

用一块带 Wi-Fi 的开发板（如 ESP32）走完"查询版本 → 下载 → 校验 → 写入 → 重启"的全流程，把串口版本的经验迁移过来。

11.5 配套思维导图

把全书压缩成一张图，八个主干、二十四个要点，对应第 1~9 章的内容。打印出来贴在显示器旁边，是最快的复习方式；窄屏设备上会自动切换为可展开的列表版本。

本章小结

  • 不同产品的 OTA 约束差异巨大：家居要无感、工业要停机窗口、医疗要变更记录。
  • 前置知识里最关键的两项是链接脚本与向量表重定位，它们决定跳转能否成功。
  • 学习顺序：读板子 → 串口烧录 → 最小 Bootloader → 校验与标志 → A/B → 验签 → 无线与云端。
  • 六个实验里，"写入中途断电"是唯一能真正验证可靠性的实验。

自测

  1. 为什么"把新固件写坏让它死循环"是一个必要的实验？
    2. 查看答案

    它能验证"看门狗复位 → 失败计数 → 达阈值自动回滚"这条链路是否真的通。很多方案的自动回滚只是写在文档里，从没被触发过。

  1. 如果只能做一个 OTA 实验，选哪个？
    2. 查看答案

    "写入中途强制断电"。它一次性检验了分区设计、标志写入顺序、元数据双副本、启动恢复这四件事是否都做对了。

B 上线前自查清单

这份清单按"能不能上线"组织，共 28 条。每一条都必须能用证据回答"是"，否则不要发第一个量产版本。

分区与启动（6 条）

  • APP 链接脚本的 ORIGIN 等于分区起始地址，且向量表在分区最前
  • 跳转函数设置了 SCB->VTOR 与 MSP，并做了 SP/PC 合法性检查
  • 跳转前关闭了中断与 Bootloader 用过的外设
  • 至少有两个可启动的固件位置（A/B 或"APP + 恢复区"）
  • Bootloader 自身有恢复手段（ROM 下载模式 / 双 BL / 备份区）
  • 分区表、链接脚本、Bootloader 三者的地址定义有单一来源，不是手工抄写

元数据与状态（5 条）

  • 升级标志/元数据有双副本，且用单调 seq 判断新旧
  • 元数据结构带整体 CRC，且 CRC 是最后写入的字段
  • 元数据里持久化了 boot_attempts、rollback_cnt 与最近错误码
  • 状态机覆盖 IDLE / DOWNLOADING / VERIFYING / PENDING / TRIAL / VALID / BAD
  • 重启后能正确恢复"上次做到哪一步"

校验与安全（7 条）

  • 分块传输有 CRC，整包有 CRC 或 SHA-256
  • 固件必须通过数字签名验证才允许提交启动标志
  • 验签失败时目标分区被标记为无效，且绝不提交标志
  • 固件头部有 hw_id，不匹配的包在下载前就被拒绝
  • 有防降级机制，且回滚走"授权白名单"而非"降低版本号"
  • 调试口在出厂前被锁定（RDP / APPROTECT 等）
  • 公钥至少有 2 个槽位，支持密钥轮换

异常与恢复（5 条）

  • 在 0%~100% 每个进度点断电测试都通过
  • 看门狗在擦除/解压/验签期间被正确喂狗，跳转后交接明确
  • 复位原因被正确区分，掉电不计入启动失败次数
  • 新固件连续启动失败 N 次后能自动回滚
  • 两个分区都坏时能进入 Recovery，而不是死循环

云端与发布（3 条）

  • 固件包不可变，版本号与构建可追溯
  • 发布有灰度阶段与可量化的放行指标
  • 设置了自动熔断阈值（成功率、回滚率）

可运维性（2 条）

  • 错误码分段定义，且能定位到具体环节（见附录 C）
  • 保留了串口/本地恢复通道，并写进售后手册

  1. 如果你的设备在升级到 50% 时断电，重启后会发生什么？
    2. 查看答案

    取决于设计。正确实现下：目标分区被标记无效、启动标志未提交、设备运行旧固件、任务状态回到可重试。如果答案是"可能变砖"，说明分区或标志设计有问题。

  1. 如果厂商私钥今天泄露，你的设备群还能被救回来吗？
    2. 查看答案

    能，前提是设备里有多个公钥槽位，且能用"另一把未泄露的私钥"签名一个替换公钥的固件。只有一个固定公钥的方案，此时已经无解。

  1. 如果新固件有严重 Bug，你多久能让全网设备回到可用状态？
    2. 查看答案

    取决于：自动回滚是否真的被测试触发过、云端是否有熔断、是否保留了串口兜底。三个都没有的话，答案是"不知道"，这本身就是最大的风险。

写在最后

OTA 的难点从来不在"把数据传过去"，而在于承认自己会犯错——固件会写错、网络会断、用户会拔电、服务器会被攻破。一个成熟的 OTA 方案，是把这些"一定会发生"的事情提前设计进去，让每一次失败都能被吸收，而不是演变成一次召回。

如果你只记住一句话：升级流程的每一步，都要能回答"如果现在断电，设备还能不能起来"。
